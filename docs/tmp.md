# 1. 서론

### 1.1. 프로젝트 개요

본 프로젝트는 LangGraph 프레임워크를 기반으로, 사용자의 대화 맥락에 따라 동적으로 반응하는 의류 추천 챗봇 시스템을 구축하여 사용자의 의도와 누적된 대화 상태(State)를 실시간으로 분석하여 그래프의 작업 흐름(Flow)을 능동적으로 결정

### 1.2. 문제 정의 및 목표

의류 추천 영역에서 챗봇이 직면하는 핵심 문제는 사용자의 모호한 요구사항과, '추천 품질'과 '응답 속도' 간의 상충 관계에 있습니다.

- **LangGraph 도입 배경:** 본 프로젝트의 초기 시스템은 사용자의 모든 입력을 '의류 검색'으로 간주하는 단일 프로세스로, "오늘 날씨 어때?"라는 일상 대화와 "청바지 찾아줘"라는 검색 요청을 구분하지 못하고 항상 검색 프로세스로 진행하는 문제점이 존재. 따라서 사용자의 의도(Intent)를 먼저 정밀하게 분석하고, 그 결과에 따라 [검색], [대화], [정보 수집], [상품 정보 조회] 등 적절한 기능으로 흐름을 동적으로 분기(Routing)할 수 있는 고도화된 아키텍처가 절실히 필요했습니다.
- **품질과 속도의 상충:** 깊이 있는 분석(LLM, 벡터 검색)을 통한 고품질 추천은 필연적으로 응답 지연을 유발하여 사용자 경험을 저해합니다. 반대로, 속도를 우선시하면 추천의 질이 저하됩니다.
- **정적 데이터의 한계:** 실시간 재고, 최신 리뷰, 가격 변동과 같은 핵심 외부 데이터를 반영하지 못해, 부정확하거나 구매로 이어질 수 없는 정보를 제공할 위험이 큽니다.

### 1.3. 핵심 해결 전략

위에서 정의한 목표를 달성하기 위해 다음과 같은 다섯 가지 핵심 전략을 수립하고 시스템을 구축했습니다.

1. **동적 상태 그래프 (LangGraph):** 대화의 모든 맥락을 `State`로 중앙에서 관리하고, `Router`를 통해 실시간으로 작업 흐름을 분기하는 동적 아키텍처를 구축했습니다.
2. **지능형 의도 분류:** 대화의 상태(정보 수집 전/후)에 따라 최적화된 프롬프트를 자동 선택하는 2단계 의도 분석 모델을 도입하여 사용자의 숨은 의도를 정확하게 파악했습니다.
3. **하이브리드 검색 엔진:** 첫 검색은 '전문가 LLM'과 '최적화된 벡터 검색'으로 심층 분석을 수행하고, 후속 요청은 '캐시'를 통해 즉각 응답하는 하이브리드 검색 엔진을 구현했습니다.
4. **실시간 데이터 연동:** ReAct 에이전트가 외부 API(Musinsa)를 지능적으로 사용하도록 설계하고, Redis/MongoDB 기반의 지능형 캐시 전략을 적용하여 실시간 정보와 빠른 응답 속도를 모두 확보했습니다.
5. **실시간 사용자 경험(UX):** SSE(Server-Sent Events) 스트리밍을 적용하고, 데이터 전송을 최적화(지연 로딩)하여 사용자가 AI의 답변 생성 과정을 실시간으로 체감할 수 있도록 구현했습니다.

## 2. 시스템 전체 아키텍처

### **2.1. 아키텍처 개요**

본 시스템의 아키텍처는 LangGraph의 동적 그래프 기능을 기반으로 설계되었으며, 크게 세 가지 핵심 축으로 구성됩니다.

1. **사용자 의도 분류 (Intent Classification):** 사용자의 모든 입력을 분석하여 '검색', '정보 질문', '일상 대화', '상품 정보 조회' 등 명확한 의도로 분류하여 사용자의 의도에 맞는 적절한 기능으로 동적으로 분기하는 핵심적인 역할 
2. **의류 검색 서브그래프 :** '의도 분류' 단계를 통해 사용자의 의도가 '검색'으로 확정되면, 실제 코디 추천을 수행하는 이 서브그래프가 실행됩니다. 서브그래프 내에서 '전문가 LLM 분석', '벡터 검색', '캐시 활용' 등의 복잡한 작업들이 유기적으로 동작하여 최종 추천 결과를 생성.
3. **실시간 상품 정보 조회 :** 사용자가 특정 상품에 대해 질문할 경우(예: 상품 클릭), 별도의 LLM 에이전트가 활성화되고 LLM에 연동된 '도구(Tool)'를 사용하여, 사용자의 질문(예: "최신 리뷰 알려줘")을 분석하고 필요한 도구를 호출합니다. 최종적으로 도구로부터 반환된 실시간 정보를 바탕으로 사용자에게 답변을 생성

### **2.3. 핵심 구성 요소: `State`, `Router`, `Node`**

- **단일 공유 상태 (State):**
그래프의 "중앙 공유 메모리" 역할을 수행합니다. `State`는 전체 대화 기록, 현재 사용자의 의도, 누적된 검색 조건, 캐시 데이터 등 대화의 모든 맥락을 단 하나의 객체에 저장하고 실시간으로 업데이트합니다. 그래프 내의 모든 노드(기능)는 이 `State`를 읽고 수정하며 작업을 수행합니다.
- **조건부 엣지 (Router):**
그래프가 동적으로 움직일 수 있게 하는 "분기점"으로 특정 기능이 실행된 후, `State`에 저장된 현재 대화의 맥락을 확인하여 다음으로 진행할 노드를 선택하여, 미리 정해진 순서가 아닌 동적인 경로를 생성.

### **2.4. 대화 영속성 보장**

매 상호작용이 끝날 때마다, `State` 객체 전체가 하나의 '스냅샷'으로 캡처되어 외부 데이터베이스(AWS RDS PostgreSQL)에 실시간으로 저장

- **맥락 유지:** 사용자가 "방금 보여준 것 중에 첫 번째 거 다시 보여줘"와 같이 이전 대화를 참조하더라도, 시스템은 DB에서 이전 `State` 스냅샷을 불러와 대화의 전체 맥락을 완벽하게 이해하고 정확한 응답을 할 수 있습니다.
- **대화 복원:** 사용자가 동일한 세션(`thread_id`)을 사용하면 DB에 저장된 마지막 대화 상태를 복원하여 중단된 지점부터 자연스럽게 대화를 이어나갈 수 있습니다.

## 3. 핵심 기능 1: 지능형 의도 분류 및 대화 관리

사용자의 입력을 정확하게 이해하고 적절한 기능으로 분기하는 '의도 분류기'입니다. 이는 `1.2. 문제 정의`에서 제기된 '선형적 아키텍처의 한계'를 극복하는 핵심 기능입니다.

### 3.1. 3가지 주요 사용자 진입 흐름

시스템은 사용자의 다양한 행동 시나리오에 대응하기 위해 3가지 주요 진입 흐름을 정의하고, 그래프의 첫 번째 라우터(Router)가 이를 감지하여 경로를 결정합니다.

1. **자연어 입력 진입 (일반 텍스트 입력):**
사용자가 채팅창에 "청바지 찾아줘" 또는 "오늘 날씨 덥다"와 같이 일반 텍스트를 입력한 경우로 사용자의 숨은 의도를 파악하는 작업부터 시작합니다.
2. **템플릿 기반 진입 (추천 버튼 클릭):**
"주말 데이트룩 찾아줘"와 같이 미리 정의된 추천 템플릿 버튼을 클릭한 경우입니다. 이 경우 사용자의 의도가 명확하므로, 복잡한 의도 분류 과정을 **생략**하고 즉시 '검색 서브그래프'로 진입시켜 신속한 사용자 경험을 제공합니다.
3. **상품 ID 기반 진입 (상품 클릭):**
사용자가 UI에서 특정 상품을 클릭하여 대화를 시작한 경우입니다. 시스템은 이를 '특정 상품에 대한 질문'으로 즉시 인지하고, 일반 검색이 아닌 `2.1`에서 언급된 '실시간 상품 정보 조회' 에이전트로 이동 

### 3.2. 의도 분류 전략

시스템은 속도와 정확성의 균형을 맞추기 위해 2단계 분류 전략을 사용합니다.

- **1단계 (빠른 분류):**
먼저, 사용자의 '최신 메시지'와 현재 그래프의 `State`(예: 정보 수집 완료 여부, 현재 검색 조건)만을 바탕으로 신속하게 1차 의도 분류를 시도합니다.
- **2단계 (심층 분류 - Fallback):**
만약 1단계에서 의도가 '불명확(unclear)'하다고 판단될 경우에만, '이전 전체 대화 기록'을 포함하는 더 넓은 문맥을 바탕으로 2차 심층 재분류를 수행합니다. 이 과정을 통해 1단계에서 놓친 맥락을 파악하여 정확도를 높입니다.

### 3.3. 의도 분류 유형 및 후속 조치

의도 분류기는 사용자의 입력을 6가지 주요 유형으로 분류하며, 각 유형에 따라 명확히 정의된 다음 노드(기능)로 작업을 전달합니다.

1. **`direct_search` (신규 검색):**
"청바지 찾아줘"와 같이 새로운 검색을 요청하는 경우입니다. '정보 수집' 기능이 실행되어 검색에 필요한 세부 정보(TPO, 스타일 등)를 파악합니다.
2. **`search_refinement` (검색 수정):**
"파란색으로 보여줘"와 같이 이미 진행된 검색의 조건을 수정하는 경우입니다. '정보 업데이트' 기능이 실행되어 기존 검색 조건을 변경하고 캐시를 초기화합니다.
3. **`info_qa` (정보 질문):**
"요즘 유행하는 스타일 알려줘"와 같이 패션 정보를 묻는 경우입니다. '정보성 질의응답' 기능이 실행되어 웹 검색 등의 도구를 활용해 답변합니다.
4. **`chatbot` (일상 대화):**
"오늘 날씨 좋다"와 같은 일반 대화입니다. '챗봇' 기능이 실행되어 대화에 응대하고, 자연스럽게 의류 추천으로 복귀하도록 유도합니다.
5. **`inappropriate_query` (부적절한 요청):**
비윤리적이거나 모욕적인 요청입니다. '부적절한 요청 처리' 기능이 실행되어 정중한 거절 메시지를 반환합니다.
6. **`unclear` (불명확):**
의도 파악이 어려운 경우입니다. `3.2`의 2단계 심층 분류를 트리거하며, 그래도 불명확할 시 '챗봇' 기능으로 전달되어 사용자에게 의도를 되묻습니다.


## 4. 핵심 기능 2:  의류 검색 엔진

'의도 분류기'를 통해 사용자의 의도가 '검색'으로 확정된 경우 동작,

### 4.1. 2가지 동작 모드

사용자의 후속 요청을 감지하여 두 가지 모드 중 하나를 동적으로 선택

1. **'신규 검색' 모드:**
    - **실행 시점:** 사용자가 처음 검색을 요청하거나("데이트룩 찾아줘"), 기존 검색 조건을 변경할 때("청바지 말고 면바지로") 실행됩니다.
    - **동작 방식:** 고품질의 정확한 추천을 위해 3명의 전문가(LLM) 의견을 바탕으로 `4.2.`에서 설명할 벡터 검색 등, 가용한 모든 리소스를 사용합니다.
    - **목표:** 사용자의 새로운 의도에 가장 일치하는 고품질의 코디 세트를 탐색합니다.
2. **'캐시 검색' 모드:**
    - **실행 시점:** 사용자가 조건 변경 없이 "다른 코디 보여줘"와 같이 추가 탐색을 요청할 때 실행됩니다.
    - **동작 방식:** 비용과 시간이 소요되는 **LLM 분석과 벡터 검색 과정을 완전히 생략하고**, '신규 검색' 시점에 그래프의 `State`에 미리 저장해 둔 캐시(K개의 검색 결과 리스트)를 참조하여, 다음 순번의 코디 세트를 즉각 반환
    - **목표:** 대화의 흐름이 끊기지 않는 즉각적인 사용자 경험(UX)을 제공

### 4.2. 벡터 검색 성능 및 정확도 최적화

'신규 검색' 모드의 품질과 속도를 극대화하기 위해, 3단계의 최적화 파이프라인을 구축

1. **1단계 (필터링): 메타데이터 사전 필터링**
LLM이 사용자 쿼리를 분석하여 "색상: 화이트", "카테고리: 셔츠"와 같은 명확한 메타데이터를 추출합니다. 이 정보를 벡터 검색 전 '사전 필터'로 적용하여, 수백만 개의 아이템 중 관련 없는 데이터를 미리 제외하고 검색 공간을 획기적으로 축소
2. **2단계 (속도): 벡터 양자화 (Quantization)**
필터링된 검색 공간 내에서, 속도를 높이기 위해 실수(float) 형태의 벡터를 정수(int)형으로 '양자화'합니다. 이를 통해 근사값을 빠르게 비교하여 K개의 관련 후보군을 신속하게 확보합니다. (속도 향상, 정확도 일부 감소)
3. **3단계 (정확도): 리랭킹 (Reranking)**
마지막으로, 2단계에서 확보한 소수의 K개 후보군에 대해서만 정밀한 리랭킹 모델을 적용합니다. 이 과정을 통해 양자화로 인해 발생할 수 있었던 순위 오류를 바로잡고, 사용자 의도에 가장 정확한 아이템이 최상단에 오도록 보장하여 최종 정확도를 극대화합니다.

### 4.3. 시나리오별 동작 과정

두 가지 동작 모드와 최적화 전략은 실제 사용자 시나리오에서 다음과 같이 유기적으로 작동합니다.

- **시나리오 1: 최초 검색 (심층 분석)**
    1. **요청:** 사용자가 "주말 데이트에 입을 캐주얼한 옷"을 입력합니다.
    2. **동작:** '신규 검색' 모드가 활성화됩니다.
    3. **실행:**
        - 3명의 전문가(LLM)가 "캐주얼", "데이트" 등의 키워드를 분석하여 검색 쿼리와 메타데이터 필터(예: '스타일: 캐주얼')를 생성합니다.
        - `4.2.`의 3단계 최적화 검색(필터링 → 양자화 → 리랭킹)을 실행하여 K개의 '상하의 코디 세트'를 확보합니다.
        - K개의 결과 리스트 전체를 그래프 `State`의 **캐시에 저장**합니다.
    4. **응답:** 캐시에 저장된 K개의 세트 중 **1순위 코디 세트**를 사용자에게 보여줍니다.
- **시나리오 2: "다른 코디 보여줘" (빠른 피드백)**
    1. **요청:** 사용자가 "다른 것도 보여줘"를 입력합니다.
    2. **동작:** 시스템이 조건 변경 없음을 인지하고 '캐시 검색' 모드를 활성화합니다.
    3. **실행:**
        - LLM 호출과 벡터 검색을 모두 생략(Skip)합니다.
        - `State`에 저장된 캐시 리스트에 접근하여, 이전에 보여준 1순위를 제외한 **2순위 코디 세트**를 즉시 가져옵니다.
    4. **응답:** 사용자에게 거의 즉각적으로 다음 추천 코디를 보여줍니다.
- **시나리오 3: 검색 조건 변경 (캐시 초기화)**
    1. **요청:** 사용자가 "좀 더 포멀한 스타일로 바꿔줘"를 입력합니다.
    2. **동작:** 시스템이 '스타일' 조건 변경을 감지하고, '신규 검색' 모드를 다시 활성화합니다.
    3. **실행:**
        - `State`에 저장되어 있던 기존 캐시(캐주얼 스타일)를 자동으로 파기(초기화)합니다.
        - *'시나리오 1'과 동일한 프로세스를 "포멀한 스타일"이라는 새로운 조건으로 다시 실행합니다.
    4. **응답:** 새로운 검색 결과(포멀한 코디)의 1순위 세트를 사용자에게 보여줍니다.

### 5.2. ReAct 에이전트 기반의 지능형 도구 활용

본 시스템의 LLM 에이전트는 **ReAct(Reason + Act)** 원칙에 따라 사용자의 질문을 받으면 필요한 도구(API)를 사용하는 방식으로 동작

- **동작 방식: '추론 → 계획 → 실행 → 응답’** LLM은 사용자의 질문을 받으면, 먼저 **자신에게 제공된 '도구 목록'(Musinsa API 기능들)**을 검토합니다.
    1. **추론 및 계획 (Reason & Plan):**
    사용자의 질문(예: "이 셔츠 최신 리뷰 요약해줘")을 해결하기 위해 어떤 도구가 필요한지 스스로 '추론'합니다. 그 결과, '리뷰를 조회하는 도구'가 필요하며, '최신순' 정렬 옵션을 인자로 사용해야 한다는 '행동 계획'을 수립합니다.
    2. **실행 (Act):**
    시스템은 LLM이 수립한 계획(사용할 도구 목록과 필요한 인자)에 따라, 실제 Musinsa API를 호출하여 실시간 데이터를 가져옵니다.
    3. **응답 (Respond):**
    API로부터 반환된 최신의 실시간 정보(Raw 데이터)를 LLM에게 전달합니다. LLM은 이 검증된 데이터를 바탕으로 "네, 최신 리뷰를 요약해 드리겠습니다. 전반적으로..."와 같이 신뢰할 수 있는 최종 답변을 생성합니다.

### 5.3. 캐시 및 비동기 처리를 통한 응답 속도 극대화

매번 도구 호출시 API 호출을 하는 것은 네트워크 상태나 외부 서버 상황에 따라 응답 지연을 유발할 수 있으므로, 이러한 지연을 방지하고 사용자에게 즉각적인 응답을 제공하기 위해 Redis **캐시**와 **비동기 작업 처리** 방식을 동시에 적용

- **캐시를 통한 API 호출 최소화 (읽기 속도 향상):**
자주 요청되는 데이터(예: 상품 정보, 리뷰)는 Redis 및 DB에 캐시로 저장하고, API 요청이 발생하면 실제 API를 호출하기 전에 캐시를 먼저 확인하여 반복적인 API 호출을 방지하고 응답 지연을 줄였습니다.
- **Task Queue를 통한 비동기 처리 (쓰기 속도 향상):**
만약 API 호출로 새로운 데이터를 가져와 Redis , DB에 저장(업데이트)해야 할 경우, 가져온 데이터를 **즉시 반환**하고, 데이터 업데이트 작업을 별도의 Task Queue(백그라운드 작업열)에 등록. 그러면 별도의 서버(Worker)에서 데이터 업데이트 작업을 진행하므로, 사용자는 DB 작업 시간을 기다릴 필요 없이 즉각적인 응답을 받을 수 있습니다.

## 6. 핵심 기능 4: 실시간 사용자 경험(UX) 구현

본 시스템은 AI의 응답을 기다리는 동안 사용자가 느끼는 지연과 정적임을 해소하고, 마치 실시간으로 대화하는 듯한 사용자 경험(UX)을 제공하는 것을 목표로 **SSE(Server-Sent Events) 스트리밍** 기술과 **데이터 지연 로딩(Lazy Loading)** 방식을 도입 

### 6.1. SSE 스트리밍을 통한 실시간 대화

AI 에이전트는 '의도 분류', '전문가 분석', '검색', '답변 생성' 등 여러 단계를 거치며, 이 과정은 수 초가 소요될 수 있습니다. 기존의 방식은 이 모든 작업이 끝날 때까지 사용자가 아무런 피드백 없이 기다려야 했습니다.

본 시스템은 **FastAPI** 서버의 `StreamingResponse` 기능과 **LangGraph**의 `astream` (비동기 스트림) 메서드를 연동하여, 작업이 완료될 때까지 기다리는 대신 **작업이 진행되는 과정 자체를 실시간으로 중계**합니다.

이를 통해 사용자는 시스템이 멈춘 것이 아니라 나를 위해 활발하게 작업 중임을 인지하게 되어, 체감 대기 시간을 획기적으로 줄이고 긍정적인 대화 경험을 제공.

### 6.2. 스트리밍 성능 최적화 (데이터 지연 로딩)

`6.1`의 스트리밍 경험을 저해하는 가장 큰 요인은 추천 상품의 이미지 URL과 같은 '무거운 데이터'입니다. 특히 보안을 위해 임시로 생성되는 AWS S3의 'Pre-signed URL'은 문자열의 길이가 매우 길어, SSE 스트림으로 직접 전송할 경우 네트워크에 큰 부담을 주어 스트리밍의 장점인 신속성을 저해합니다.

이 문제를 해결하기 위해, 본 시스템은 **'지연 로딩(Lazy Loading)' 아키텍처**를 설계하여 스트림 데이터와 상세 데이터를 완벽하게 분리했습니다.

- **동작 방식:**
    1. **1단계 (SSE 스트림): 가벼운 ID 전송**
    AI 서버(FastAPI)는 SSE 스트림을 통해 텍스트 메시지와 함께, 무거운 이미지 URL 대신 **가벼운 상품 ID 목록**(`["P12345", "P67890"]`)만을 전송
    2. **2단계 (REST API): 상세 정보 지연 로딩**
    클라이언트(프론트엔드)는 이 가벼운 상품 ID 목록을 수신한 직후, 이 ID들을 가지고 백엔드에 **별도의 REST API를 호출**합니다.
    3. **3단계 (API 응답): 메타데이터 및 Pre-signed URL 전송**
    해당 REST API는 요청받은 상품 ID에 대한 상세 정보(메타데이터, 가격, 브랜드 등)와 함께, 이미지를 다운로드할 수 있는 접근 권한이 부여된 URL을 생성하여 클라이언트에 응답합니다.

## 7. 테스트 및 모니터링 환경

복잡한 동적 그래프 아키텍처는 실행 흐름을 예측하고 디버깅하기 어려운 문제를 해결하기 위해 시스템의 모든 동작을 투명하게 검증하고 모니터링할 수 있는 시스템 구축

### 7.1. Streamlit 기반 통합 테스트 및 검증 환경

개발 검증을 위해, 실제 서비스 환경과 유사한 UI를 제공하는 **Streamlit 테스트 서버**를 구축하 시나리오별 시각적 검증을 가능하게 합니다.

 `3.1.`에서 정의한 3가지 주요 진입 흐름(상품 ID 입력, 템플릿 선택, 일반 텍스트 입력)을 직접 시뮬레이션하며 `master_router`의 동작을 검증할 수 있습니다.

또한, 이 환경은 '의도 분석', '검색 서브그래프', 'Musinsa API 에이전트' 등 핵심 모듈을 개별적으로 실행하고, 스트리밍 텍스트나 실제 반환되는 추천 이미지(코디 세트)를 시각적으로 직접 확인하는 **모듈 단위 기능 검증**도 지원합니다.

### 7.2. **Langfuse 연동을 통한 추적 및 모니터링**

모든 테스트와 실제 운영 환경에서의 동작을 투명하게 모니터링하기 위해, LLM 애플리케이션 추적 도구인 **Langfuse**를 시스템에 연동했습니다.

Langfuse 대시보드를 통해, LangGraph에서 발생한 모든 상호작용을 **시각적으로 추적(Trace)**할 수 있습니다.

- **실행 흐름 시각화:** 사용자의 입력 하나가 어떤 `Router`를 거쳐 어떤 `Node`들로 전달되었는지 전체 흐름을 시각적으로 확인합니다.
- **상세 입출력 로깅:** 각 노드(기능)가 실행될 때 사용한 프롬프트, LLM의 응답, 도구 호출 결과 등 모든 입출력 데이터를 상세히 로깅합니다.
- **성능 및 비용 분석:** 각 노드(기능)가 실행되는 데 걸린 시간(Latency)과, **LLM 호출에 사용된 토큰 비용(Cost)**을 상세히 측정하여, 시스템의 병목 구간 식별 및 운영 비용 최적화에 활용합니다

이러한 테스트 및 모니터링 환경 구축을 통해, 복잡한 에이전트 시스템의 안정성과 신뢰도를 확보할 수 있었습니다.

## 주요 노드 설명

### 가. `intent_classify_node`:

- **역할**: 사용자의 모든 발화 뒤에 숨겨진 **핵심 의도(Intent)**를 파악하여, 다음에 어떤 작업을 수행해야 할지 결정하는 가장 첫 번째 관문입니다.
- **동작 방식**:
    1. **1단계 (빠른 분류)**: 먼저 사용자의 최신 메시지만으로 '검색', '정보 질문', '일상 대화' 등 6가지 의도 중 하나로 빠르게 분류합니다.
    2. **2단계 (심층 분류)**: 만약 1단계에서 의도가 "불명확(`unclear`)"하다고 판단되면, 이 노드는 대화의 전체 맥락을 파악하기 위해 이전 대화 기록까지 포함하여 더 깊이 있게 재분류를 시도합니다.
- **중요성**: 이 노드가 없다면, 시스템은 사용자가 "오늘 날씨 좋네요"라고 말했을 때와 "데이트룩 찾아줘"라고 말했을 때를 구분하지 못하고 모든 입력을 검색으로 처리하려 할 것입니다. `intent_classify_node`는 사용자의 의도에 맞는 최적의 경험(대화, 정보 제공, 검색)을 제공하기 위한 첫 단추를 꿰는 핵심적인 역할을 합니다.

### 나. `information_gathering_node`:

- **역할**: 사용자의 의도가 '검색'으로 파악되었을 때, 성공적인 검색에 필수적인 정보(TPO, 스타일, 색상)를 수집하는 역할을 합니다.
- **동작 방식**:
    1. **정보 추출**: 사용자의 메시지("주말 데이트에 입을 캐주얼한 옷")에서 `extraction_prompt`를 이용해 `tpo: '데이트'`, `style: '캐주얼'`과 같은 구조화된 정보를 추출하여 `State`의 `cloth_search` 필드를 채웁니다.
    2. **되묻기**: 만약 '색상' 정보가 누락되었다면, 이 노드는 `generation_prompt`를 사용하여 "주말 데이트에 입을 캐주얼한 스타일을 찾으시는군요! 혹시 선호하는 색상이 있으신가요?"와 같이 부족한 정보를 자연스럽게 물어보는 질문을 생성합니다.
- **중요성**: 이 노드는 사용자의 모호한 요구사항을 명확한 검색 조건으로 구체화하는 핵심적인 단계입니다. 이 과정이 없다면, `search_subgraph`는 무엇을 검색해야 할지 알 수 없어 제대로 동작할 수 없습니다.

### 다. `information_update_node`: 사용자의 피드백을 반영하는 조율사

- **역할**: 이미 검색이 한 번 이상 진행된 상태에서, 사용자의 추가적인 요구사항("청바지 말고 면바지로 보여줘")을 반영하여 검색 조건을 수정노드
- **동작 방식**:
    1. `update_prompt`를 사용하여 사용자의 피드백을 해석하고, `State`의 `cloth_search`를 새로운 조건(예: `style: '면바지'`)으로 업데이트합니다.
    2. **가장 중요한 역할**로, 새로운 검색을 위해 기존의 검색 결과가 저장된 **`expert_search_cache`를 초기화**합니다. 이 초기화 작업이 바로 `search_subgraph`가 '캐시 검색'이 아닌 '신규 검색'을 다시 시작하도록 만드는 신호탄이 됩니다.
- **중요성**: 사용자와의 연속적인 상호작용을 통해 추천 결과의 만족도를 점진적으로 높여나가는, 대화형 추천 시스템의 핵심적인 기능을 담당합니다.

### 마. `chatbot_node`: 대화를 부드럽게 만드는 윤활유

- **역할**: 사용자가 의류와 관련 없는 일상적인 대화를 시도할 때, 자연스럽게 응대하며 대화의 흐름이 끊기지 않도록 하는 '윤활유' 같은 역할을 합니다.
- **동작 방식**: "오늘 너무 덥다"와 같은 메시지에 "정말 덥네요! 이런 날씨에 입기 좋은 시원한 옷을 찾아드릴까요?"처럼, 사용자의 말에 공감하면서도 자연스럽게 본래의 목적인 의류 추천으로 대화를 유도합니다.
- **중요성**: 이 노드가 없다면 시스템은 사용자의 모든 입력을 기능적으로만 처리하려 하여 딱딱하고 비인간적인 느낌을 줄 수 있습니다. `chatbot_node`는 시스템에 인간적인 면모를 부여하여 사용자에게 훨씬 더 긍정적인 대화 경험을 제공합니다.

### 사. `info_qa_node`

- 역할 : 패션 관련 정보 질문에 답변합니다.
- 해당 노드에는 내부에 있는 llm이 사용자 요청에 대해 거짓된 정보를 응답하지 않도록 웹 검색 도구를 이용하여 정확하고 최신정보를 가져와서 응답할 수 있도록 동작

## 4. SSE를 통한 스트리밍 통신:

AI의 답변을 기다리는 동안 느끼는 지루함을 없애고, 마치 실시간으로 대화하는 듯한 사용자 경험(UX)을 제공하기 위해 **SSE(Server-Sent Events)** 방식의 스트리밍 통신을 구현했습니다.

### 나. 시스템 전체의 비동기 데이터 흐름

사용자의 메시지 하나가 최종 답변으로 돌아오기까지의 전체 시스템 흐름은 다음과 같습니다.

1. **(Front-End)**: 사용자가 메시지를 입력하고 '전송' 버튼을 누릅니다.
2. **→ (Spring Server)**: 백엔드 서버는 요청을 받아 AI 서버로 즉시 전달하는 중개자(Proxy) 역할을 합니다.
3. **→ (AI Server - FastAPI)**: LangGraph 에이전트가 작업을 시작합니다.
4. **← (SSE Connection)**: AI 서버는 작업이 끝나기를 기다리지 않고, **즉시 클라이언트와 SSE 연결을 엽니다.**
5. **← (실시간 업데이트 전송)**: 이후 그래프의 각 노드가 실행되거나 LLM이 답변을 생성하는 매 순간, 다음과 같은 업데이트가 SSE 연결을 통해 실시간으로 클라이언트에 전송됩니다.
    - `"type": "status", "content": "사용자 의도 분석 중..."`
    - `"type": "status", "content": "스타일 전문가 의견 생성 중..."`
    - `"type": "token", "content": "이런"`
    - `"type": "token", "content": "스타일은"`
    - `"type": "token", "content": "어떠세요?"`
    - `"type": "message", ...` (최종 추천 결과)

**3) API 응답 최적화: Redis 캐시와 Task Queue를 활용한 비동기 처리**

클라이언트가 요청하는 `GET /api/search/{product_id}` 엔드포인트는 단순한 DB 조회가 아닌, **성능과 안정성을 극대화하기 위한 다단계 처리 로직**을 수행합니다.

1. **1단계: Redis 캐시 확인 (가장 빠른 경로)**
    - 요청이 들어오면 가장 먼저 **Redis 캐시**에 해당 상품 데이터가 있는지 확인합니다.
    - **Cache Hit**: 데이터가 존재하면, 만료되었을 수 있는 이미지 URL만 AWS S3 Pre-signed URL로 새로 발급하여 즉시 사용자에게 응답합니다. 이 과정은 100ms 미만으로 매우 빠릅니다.
2. **2단계: Cache Miss 시 병렬 조회**
    - 캐시에 데이터가 없으면, **MongoDB**에서 상품의 메타 정보를 가져오는 작업과 **Musinsa API**에서 실시간 가격 정보를 가져오는 작업을 `asyncio.gather`를 통해 **동시에 병렬로 실행**하여 대기 시간을 최소화합니다.
3. **3단계: 실시간 정보 기반 응답 및 비동기 후처리**
    - **(API 호출 성공 시)** 최신 가격 정보와 DB 정보를 조합하여 **사용자에게 즉시 응답을 반환**합니다. 사용자는 더 이상 기다릴 필요가 없습니다.
    - 동시에, 이 새로운 정보를 **캐시와 DB에 업데이트하는 느린 작업을 `TaskQueue`(ARQ)에 '작업(Task)'으로 등록**합니다. (`src/taskqueue/client.py`)
    - 별도의 **Worker 서버**(`src/taskqueue/worker.py`)가 이 작업을 비동기적으로 가져가 백그라운드에서 데이터 업데이트를 처리합니다. 이를 통해 **사용자 응답 시간과 무거운 백그라운드 작업을 완벽하게 분리**했습니다.
4. **4단계: 안정성을 위한 폴백(Fallback) 메커니즘**
    - 만약 Musinsa API 호출이 **실패(예: 429 Rate Limit 에러)**하더라도, 시스템은 에러를 반환하는 대신 MongoDB에 저장된 **기존 가격 정보를 사용하여 사용자에게 응답**합니다. 이 '폴백' 메커니즘 덕분에 외부 API의 일시적인 문제에도 서비스는 중단 없이 안정적으로 동작합니다.
