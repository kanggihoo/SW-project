# AI 측 개발진행 사항

1. 벡터 검색을 위한 데이터 파이프라인 구축
2. 쿼리 분석 llm 을 이용한 벡터 검색 정확도 증대 

## 데이터 파이프라인 구축의 필요성 (최종 수정본)

### **🎯 목표**

사용자가 **자연어**로 실제 쇼핑몰에서 **현재 구매 가능한 의류 상품을 정확하게 검색**할 수 있는 시스템을 구축하는 것입니다.(벡터 검색을 이용한 유사도 기반 의류검색)

### **📋 필요사항**

1. **벡터 데이터베이스 (Vector DB)**: 사용자의 검색어와 의미적으로 가장 유사한 상품을 찾기 위한 핵심 기술입니다.
2. **고품질 캡션 (Caption)**: 각 의류 이미지의 디자인, 스타일, 핏 등을 풍부하게 설명하는 텍스트 정보가 필요합니다. 이 캡션이 벡터로 변환되어 DB에 저장됩니다.
3. **캡션 생성 AI (LLM)**: 의류 이미지로부터 고품질 캡션을 자동으로 생성하는 역할을 담당합니다.
4. **정제된 입력 데이터**: AI가 정확하고 일관된 캡션을 생성하기 위해서는 분석에 필요한 정보만 담긴 **깨끗하고 구조화된 의류 이미지**를 입력값으로 제공해야 합니다.

### **⚠️ 문제점**

실제 쇼핑몰의 원본 이미지는 AI 입력값으로 사용하기에 부적합한 **'긴 복합 이미지'** 형태라는 점입니다. 이 이미지 안에는 다음과 같은 정보들이 뒤섞여 있습니다.

- **의류 관련 이미지**: 모델 착용샷, 제품 단독샷, 디테일 확대 이미지 등
- **텍스트 정보 이미지**: 사이즈 표, 소재, 세탁법 등
- **그 외의 필요없는 정보가 담긴 이미지 :** 브랜드 로고, 의류 확대 이미지

이처럼 정제되지 않은 이미지를 그대로 AI에 입력하면, AI가 어떤 부분에 집중해야 할지 판단하지 못해 **저품질의 캡션을 생성 및 비용 비효율적** 

### **💡 해결방안**

'긴 복합 이미지'를 AI가 처리할 수 있는 형태로 가공하기 위해 **데이터 파이프라인을 구축**했습니다. 이 파이프라인은 원본 이미지에서 아래 두 가지 종류의 데이터를 체계적으로 추출합니다.

1. **캡션 생성용 의류 이미지 추출**:
    - AI가 의류의 특징을 정확히 분석할 수 있도록 모델 착용샷, 제품 단독샷 등 **깨끗한 의류 이미지만을 분리**합니다.
    - 이 이미지들을 기반으로 생성된 캡션은 벡터로 변환되어 **벡터 검색의 핵심 데이터**로 활용됩니다.
2. **메타 정보 추출용 텍스트 이미지 추출**:
    - 사이즈, 소재, 세탁법 등의 정보가 담긴 **텍스트 부분 이미지를 따로 분리**합니다.
    - AI의 OCR 기능을 이용해 텍스트를 추출하고, 이 정보는 검색 결과에서 사용자에게 **제품의 상세 정보를 제공**하는 용도로 활용됩니다.

## 쿼리 분석 LLM 개발의 필요성

### **🎯 목표**

**사용자의 복잡하고 미묘한 의도까지 완벽하게 이해**하고 최적의 검색 결과를 반환하기 위해, 검색어 자체를 지능적으로 분석하고 가공하는 **'쿼리 분석 LLM'을 개발**하는 것입니다.

### **⚠️ 문제점 (해당 기능이 없다면 발생하는 문제)**

1. **'복합 쿼리' 처리 불가**
    - 사용자가 "출근할 때 입을 청바지랑 흰색 반팔"처럼 여러 아이템을 동시에 검색하면, 시스템은 이를 하나의 어중간한 의미를 가진 벡터로 만듭니다.
    - 결과적으로 청바지나 반팔 중 **한 종류의 아이템만 보여주거나, 의도와 전혀 다른 상품을 반환**하는 등 검색 결과가 매우 부정확해집니다.
2. **사용자와 데이터베이스 간의 언어 불일치**
    - 사용자는 "티셔츠", "반팔티" 등 자유로운 일상 용어를 사용하지만, DB에는 'T-shirt'와 같이 정형화된 데이터가 저장되어 있습니다.
    - 이 언어 차이 때문에 **정확한 사전 필터링(pre-filtering)이 불가능**하여 검색 속도가 느려지고 정확도가 떨어집니다.
3. **벡터 검색 정확도의 한계**
    - AI가 상품 캡션을 '회사룩'이라는 키워드로 생성했을 때, 사용자가 유사어인 '오피스룩'으로 검색하면 의미적 유사성 때문에 어느 정도 결과는 나오지만, **최상의 정확도를 보장할 수 없습니다.**
    - 결국 벡터 DB가 가진 잠재적 성능을 최대로 끌어내지 못하고, **가장 관련성 높은 상품을 놓칠 수 있습니다.**

### **✨ 기대효과**

1. **'복합 쿼리'에 대한 완벽한 분해 및 검색**
    - 쿼리 분석 LLM이 "출근용 청바지"와 "출근용 흰색 반팔"이라는 **두 개의 독립된 검색 의도로 명확하게 분리**합니다.
    - 각 의도에 맞춰 개별 검색을 동시에 수행하여, 사용자가 기대한 대로 **상의와 하의를 모두 정확하게 찾아 제시**할 수 있습니다.
2. **지능형 번역을 통한 정확한 필터링**
    - LLM이 '지능형 번역가'처럼 사용자의 언어("티셔츠")를 DB의 언어(`sub_category: 'T-shirt'`)로 **자동 변환**합니다.
    - 이를 통해 정확한 db에 대한 **필터링이 가능**해져 검색 시스템의 전반적인 속도와 정확도가 대폭 향상됩니다.
3. **'쿼리 재구성'을 통한 검색 정확도 극대화**
    - LLM이 사용자의 쿼리("오피스룩")를 DB의 캡션 데이터가 가장 잘 이해할 수 있는 **최적의 키워드("회사룩")로 재구성**하여 검색을 실행합니다.
    - 벡터 DB와의 소통을 최적화하여 벡터 유사도 점수를 극대화함으로써, **검색 정확도를 최상으로 끌어올립니다.**

### 2. 쿼리 분석 LLM 개발의 필요성

단순히 사용자의 검색어를 임베딩하여 벡터 DB에서 검색하는 방식은 한계가 명확합니다. 사용자의 복잡하고 미묘한 의도를 시스템이 완벽하게 이해하고 최적의 결과를 반환하게 하려면, 검색어 자체를 지능적으로 분석하고 가공하는 **'쿼리 분석 LLM'**이 반드시 필요합니다.

### 2.1. 문제점: LLM 없이는 '복합 쿼리'를 처리할 수 없음

사용자는 흔히 여러 아이템을 동시에 검색합니다. 예를 들어, **"출근할 때 입을 만한 청바지랑 흰색 반팔"** 이라고 검색했다고 가정해 보겠습니다.

- **기대하는 결과:** '출근용'이라는 TPO에 맞는 청바지(하의)와 흰색 반팔(상의) 이미지가 모두 검색 결과로 나와야 합니다.
- **LLM이 없을 때의 결과:** 시스템은 "청바지"와 "흰색 반팔"이라는 키워드가 섞인 하나의 긴 쿼리 벡터를 만듭니다. 이 벡터는 청바지에도, 반팔에도 완벽히 일치하지 않는 **어중간한 의미**를 갖게 되어, 사용자가 의도한대로 상의와 하의를 명확히 구분하여 찾아주지 못하거나, 한 종류의 아이템만 보여주는 등 검색 결과가 제한적으로 동작합니다.

**쿼리 분석 LLM**은 이 문제를 해결합니다. 저희가 설계한 **2-Call 아키텍처**는 이 복합 쿼리를 **"출근용 청바지"**와 **"출근용 흰색 반팔"** 이라는 두 개의 독립된 검색 의도로 명확하게 분리합니다. 이를 통해 각 아이템에 대한 개별적인 벡터 검색을 병렬로 수행하여, 사용자가 기대한 대로 관련된 상의와 하의를 모두 정확하게 찾아 제시할 수 있습니다.

### 2.2. 문제점: 사용자의 언어와 DB의 언어가 다름

검색 성능을 높이려면 벡터 검색 전에 1차적으로 검색 대상을 좁히는 **'사전 필터링'**이 매우 중요합니다. 하지만 여기서 사용자의 언어와 DB에 저장된 데이터의 언어가 달라 문제가 발생합니다.

- **사용자의 언어:** "티셔츠", "티", "반팔티" 등 자유롭게 표현합니다.
- **DB의 언어:** `sub_category` 필드에는 'T-shirt' 와 같이 정해진 영문/단일 표기로 저장되어 있습니다.

**쿼리 분석 LLM**은 이 간극을 메우는 **'지능형 번역가'** 역할을 합니다. 사용자가 "티셔츠"라고 입력하면, LLM이 이를 DB의 `sub_category: 'T-shirt'` 라는 **정형화된 필터 조건으로 변환**해 줍니다. 이 덕분에 부정확한 키워드 매칭이 아닌, 명확한 카테고리 필터링이 가능해져 검색의 속도와 정확도가 대폭 향상됩니다.

### 2.3. 문제점: 벡터 검색의 정확도를 최대로 끌어올릴 수 없음

벡터 임베딩은 유의어(예: 오피스, 회사)를 어느 정도 이해하지만, 최고의 검색 정확도를 위해서는 **캡션 생성에 사용된 단어와 가장 유사한 단어로 검색**하는 것이 유리합니다.

- **상황:** 캡션을 생성할 때, AI가 `TPO` 정보를 '회사룩'이라는 키워드를 중심으로 생성했다고 가정해 봅시다. 해당 의류의 벡터는 '회사룩'이라는 단어와 가장 강한 의미적 연결을 갖게 됩니다.
- **사용자 쿼리:** 사용자는 "오피스룩" 또는 "출근룩"으로 검색할 수 있습니다.
- **한계:** 임베딩 모델이 '오피스룩'과 '회사룩'의 유사도를 높게 판단하더라도, '회사룩'으로 직접 검색하는 것보다는 정확도가 떨어질 수밖에 없습니다.

**쿼리 분석 LLM**은 **'쿼리 재구성(Rewritten Query)'**을 통해 이 문제를 해결합니다. LLM은 사용자의 "오피스룩"이라는 쿼리를 DB 데이터(캡션)가 가장 잘 이해할 수 있는 **'회사룩'이라는 최적의 키워드로 변환하여 검색**을 실행합니다. 즉, 벡터 DB와 가장 효과적으로 소통할 수 있는 언어로 쿼리를 재작성함으로써, **벡터 유사도 점수를 극대화하고 검색 정확도를 최상으로 끌어올리는** 핵심적인 역할을 수행합니다.

# 벡터 검색 기반 의류 추천 시스템을 위한 End-to-End 데이터 파이프라인 구축

## 단계별 과정 요약

1. **데이터 수집**: 실제 의류 사이트를 크롤링(무신사)
2. **데이터 전처리**: OpenCV**와 **Numpy**를 이용해 긴 이미지를 적절하게 분리하고 합치는 작업을 포함한 전처리 과정
3. **데이터 저장**: 수집한 데이터를 MongoDB, AWS S3, DynamoDB에 효율적으로 저장.
4. **캡션 작업 환경 구현**: PySide6를 활용해 여러 사용자가 캡션 작업에 쓸 구조화된 데이터를 선택할 수 있는 GUI 앱을 개발
5. **캡션 데이터 생성** : 구축한 앱을 이용해 캡션 작업에 필요한 데이터 생성
6. **벡터 검색용 데이터 추출**: LLM**(거대 언어 모델)을 활용해 이미지에 대한 캡션 및 관련 추가 정보를 추출
7. **캡션 벡터화**: Jina 임베딩 모델**을 사용해 생성된 캡션을 벡터로 변환
8. **벡터 DB 저장**: 벡터 데이터를 MongoDB Atlas에 저장

### 1. 데이터 수집(크롤링)

본 프로젝트의 핵심 기능인 벡터 검색 모델 개발을 위한 데이터셋 구축을 목표로, 국내 대표 패션 플랫폼 '무신사(MUSINSA)'의 남성 의류 데이터를 수집했습니다. 데이터 수집은 **Python** 기반의 **Selenium**과 **BeautifulSoup** 라이브러리를 활용하여 2단계로 진행

**1단계**에서는 Selenium을 통해 웹 페이지의 동적 요소인 '무한 스크롤'을 자동화하여 전체 상품 목록에 접근했으며, 각 상품의 기본 정보(제품명, 상세 페이지 링크 등)를 추출하여 CSV 파일로 1차 저장

**2단계**에서는 1단계에서 생성된 CSV 파일을 기반으로 각 상품의 상세 페이지에 개별적으로 접근하여 제품 이미지, 사용자 리뷰, 그리고 의류 관련 메타 데이터(소재, 사이즈, 브랜드 등)와 같은 상세 정보를 추가로 수집

### 2. 데이터 전처리

이전 단계에서 수집된 이미지는 여러 제품 사진, 모델 착용샷, 사이즈 정보, 설명 텍스트 등이 한데 섞여 있는 **긴 복합 이미지 형태**였습니다. 따라서 **캡션 작업에 바로 활용하기 어려워, 의미 있는 단위로 이미지를 분할하는 정교한 전처리 과정이 반드시 필요**합니다.

본 프로젝트에서는 **OpenCV**와 **NumPy**를 활용하여 이미지 분할 알고리즘을 직접 구현.

핵심 전략은 이미지들 사이를 구분하는 **'흰색 공백 영역'을 탐지**하는 것이었습니다. **특정 행(row)이 공백 영역인지 판단**하기 위해3가지의 조건을 만족하는 경우로 공백인지로 판단

①각 픽셀 채널의 평균값이 특정 임계치 이상

②행 내에 어두운 픽셀(텍스트 등)이 일정 개수 미만 (대부분의 흰색 영역에 글자가 있는 경우 방지) 

③인접 행과의 픽셀 값 차이가 크지 않아야 한다 (흰색 영역에 흰색 의류 이미지가 존재하는 경우 방지) 

위의 과정을 통해 특정 행이 분활해야 하는 점인지 아닌지를 판단.

이전 작업을 통해 얻은 결과를 바탕으로 이미지 내에서 **실질적인 정보가 연속적으로 나타나는 구간을 1차적으로 식별하여** 각 연속된 콘텐츠 덩어리의 **시작점(top)과 끝점(bottom)**을 좌표 형태로 추출. 추출된 값들 중에서 시작점과 끝점과의 거리가 특정 임계값(Threshold)보다 작은 영역들은 단순한 오류나 잡음(Noise)으로 간주하여 제거하고,  인접한 두 영역, 즉 `(시작점1, 끝점1)`과 `(시작점2, 끝점2)` 간격이 이 매우 좁을 경우, 이 두 영역이 사실상 하나의 의미로 간주하여 병합하여 최종 컨텐츠 영역 판단. 마지막으로, 결정된 각 영역의 상하에 패딩을 추가하여 이미지 분할작업 진행. 

최종적으로 분할된 이미지의 가로 세로 비율을 고려해서 width가 height에 비해 너무 긴 경우는 ‘**텍스트 이미지**’로, 그렇지 않은 경우는 '**제품 관련 이미지**'로 분류 해서 각각 `text` 폴더와 `segment` 폴더에 저장하고 원본 긴 복합 이미지는 `detail` 영역에, 제품에 대한 썸네일 이미지는 `summary` 폴더에 체계적으로 저장.

`text` 폴더에 저장된 이미지에 대해서는 동일한 원본으로 부터 분리된 **여러 텍스트 조각들을 다시 하나의 이미지로 합쳐 정보의 연속성을 복원**하여 최종적인 데이터 전처리 과정 

<aside>
💡

**⚙️ 알고리즘 상세 과정**:

1. **1단계: 흰색 공백 행(Row) 탐지 (`get_white_rows` 로직)**
    - **조건 1 (Mean & Count 기반):** `get_white_rows_by_meancount` 함수를 통해 각 행이 아래 두 조건을 동시에 만족하는지 검사합니다.
        - **밝기 조건**: 행의 평균 픽셀 값이 `mean_threshold` 이상으로 충분히 밝은가?
        - **텍스트 제외 조건**: 행 내에 `dark_threshold`보다 어두운 픽셀 수가 `dark_threshold_count` 미만인가? (흰 바탕의 검은 글씨를 공백으로 판단하는 것 방지)
    - **조건 2 (Difference 기반):** `get_white_rows_by_diff` 함수를 통해 흰색 의류와 실제 공백을 구분합니다.
        - 행 내 가로 방향 픽셀 간의 차이를 계산하여, 그 변화량(`log_max_mean`)이 `log_threshold`보다 낮은지 확인합니다. (변화가 거의 없는 균일한 영역, 즉 실제 공백일 가능성이 높음)
    - 위 두 가지 주요 로직을 통과한 행만이 최종적으로 '흰색 공백 행'으로 판별됩니다.
2. **2단계: 콘텐츠 영역 1차 추출 (`find_content_regions`)**
    - 1단계에서 생성된 '흰색 공백 행' boolean 리스트를 입력받습니다.
    - `white_rows`가 `False`인, 즉 콘텐츠가 연속되는 구간의 `(시작점, 끝점)`을 찾아 리스트로 반환합니다.
3. **3단계: 콘텐츠 영역 정제 및 최종 분할 지점 계산 (`process_content_regions`)**
    - 2단계에서 추출된 원본 콘텐츠 영역 리스트를 입력받아 후처리를 진행합니다.
    - **노이즈 제거**: 영역의 높이가 `min_content_height`보다 작으면 유의미한 콘텐츠가 아니라고 판단하여 제거합니다.
    - **영역 병합**: 두 영역 사이의 공백이 `min_white_gap`보다 작으면, 사실상 하나의 콘텐츠라고 판단하여 두 영역을 합칩니다.
    - **여백 추가**: 최종 결정된 각 영역의 상하에 `padding`을 추가하여, 경계선에서 이미지가 잘리는 현상을 방지합니다.
4. **4단계: 실제 이미지 분할 (`segment_image_by_content`)**
    - 위 모든 함수를 순서대로 호출하여 최종 분할 지점 리스트를 얻습니다.
    - Python의 Pillow(PIL) 라이브러리의 `crop` 기능을 사용해 원본 이미지를 해당 지점별로 잘라내어 개별 이미지 파일로 생성합니다.
5. **5단계: 분활된 이미지 분류**
    - 4단계에서 생성된 각 이미지 조각(`seg`)에 대해 **`is_wide_image`** 함수를 적용하여 분류를 수행합니다.
    - **분류 기준**: 이미지의 **가로-세로 비율 (Aspect Ratio)**.
    - **판단 로직**: `이미지 가로 길이 / 이미지 세로 길이 > 임계값(threshold_ratio, 기본값 8.0)` 조건을 만족하는지 확인합니다.
        - **True (텍스트 이미지)**: 가로 길이가 세로 길이에 비해 8배 이상 긴 경우. 이는 여러 줄의 텍스트가 모여있는 넓고 짧은 형태의 이미지일 가능성이 높다고 판단합니다.
        - **False (제품 이미지)**: 그 외의 경우. 정사각형 또는 세로로 긴 형태를 가지는 일반적인 제품/모델 이미일 가능성이 높다고 판단합니다.
    - 최종적으로 `(분할된 이미지, 텍스트 여부 boolean)` 형태의 튜플로 묶어 결과 리스트에 추가합니다.
6. **6단계: 분할된 텍스트 이미지 병합**
    - **목표**: `text` 폴더 안에 있는, 동일한 원본에서 분리된 여러 텍스트 조각들을 다시 하나의 이미지로 합쳐 정보의 연속성을 복원합니다.
    - **실행 함수**: `merge_segmented_images`
    - **작동 방식**:
        1. **그룹화(Grouping)**: `text` 폴더 내의 모든 이미지 파일명을 파싱합니다. 파일명 형식인 **`{original_index}_{segment_index}.jpg`** 을 기준으로, 동일한 **`original_index`** 를 가진 이미지들의 경로를 하나의 그룹으로 묶습니다.
        2. **정렬(Sorting)**: 각 그룹 내에서 **`segment_index`** 를 기준으로 오름차순 정렬(`natsorted` 사용)합니다. 이를 통해 원본 이미지에 있던 텍스트의 순서를 그대로 복원합니다.
        3. **병합(Merging)**: 정렬된 순서에 따라 이미지 조각들을 세로 방향으로 하나씩 이어 붙여(**`Image.paste`**), 새로운 단일 이미지(`merged_{original_index}.jpg`)를 생성합니다. 이 과정에서 너무 작아 무의미한 조각(예: 높이 10px 미만)은 제외하여 최종 결과물의 품질을 높입니다.
        4. **정리(Cleanup)**: 병합이 완료되면, 원본이 되었던 개별 텍스트 조각 파일들을 삭제하여 데이터 중복을 방지하고 저장 공간을 효율적으로 관리합니다.
</aside>

- **Before & After**: 원본 긴 이미지 하나와, 그 이미지가 분할/분류되어 각 폴더(`segment`, `text`)에 저장된 결과물을 나란히 보여주면 전처리 효과를 직관적으로 증명할 수 있습니다.
- **알고리즘 순서도**: 흰색 행 판단 -> 영역 추출 -> 영역 정제 -> 최종 분류로 이어지는 알고리즘의 로직을 간단한 순서도로 그리면 복잡한 과정을 쉽게 전달할 수 있습니다.
    
    **📝 최종 결과물**: 원본(`detail`), 썸네일(`summary`), **분할된 제품 이미지(`segment`)**, **분할된 텍스트 이미지(`text`)** 폴더로 구조화하여 저장.
    

### 3. 데이터 저장

데이터의 성격과 향후 활용 목적을 고려해서 크롤링 및 전처리를 통해 확보된 데이터는 **MongoDB, AWS S3, AWS DynamoDB** 세 곳에 분산 저장.

**MongoDB**에는 상품의 가격, 리뷰, 사이즈 등 원본 메타데이터를 저장하여 유연한 데이터 조회 

**AWS S3**는 전처리된 모든 이미지 에셋(`detail`, `segment` , `summary` , `text` 폴더 안의 이미지)의 중앙 저장소로 활용하여 대용량 파일을 안정적으로 보관하고, IAM 인증을 통해 팀원 간의 효율적인 데이터 공유 환경구축.

향후 진행될 캡션 작업의 효율성과 비용을 최적화하기 위해 **AWS DynamoDB**를 **인덱싱 데이터베이스로 도입**. S3의 `List` API는 호출 비용이 높은 반면, DynamoDB는 특정 항목 조회 비용이 매우 저렴합니다. 이러한 특성을 활용하여 DynamoDB에 `product_id`와 그에 해당하는 S3 내 이미지들의 '파일명'만 저장.

이를 통해 후속 작업에서 **S3의 폴더를 스캔할 필요 없이, DynamoDB 조회 한 번으로 필요한 모든 이미지의 S3 경로(Key)를 즉시 생성하여 저렴한 `Get` API만으로 파일에 접근하는 비용 효율적인 데이터 파이프라인을 완성**

<aside>
💡

### **1. MongoDB: 상품 메타데이터 저장소**

- **🗂️ 저장 대상 (What)**: 크롤링으로 수집한 상품의 핵심 텍스트 데이터.
    - (예: 상품명, 브랜드, 가격, 색상/사이즈 옵션, 전체 리뷰, 평점 등)
- **💡 선택 이유 (Why)**:
    - **유연한 스키마**: 비정형적인 웹 상품 정보를 있는 그대로 저장하기에 용이.
    - **원본 데이터 보관**: 모든 정보의 원천이 되는 마스터 데이터베이스 역할.

### **2. AWS S3: 이미지 자산 및 핵심 정보 저장소**

- **🖼️ 저장 대상 (What)**:
    - 전처리된 모든 이미지 파일: `main_category/sub_category/product_id/` 경로 하위에 `detail/`, `summary/`, `segment/`, `text/` 폴더 구조를 유지하며 저장.
    - 각 상품의 핵심 정보 요약본: `main_category/sub_category/product_id/meta.json`
- **💡 선택 이유 (Why)**:
    - **확장성 및 안정성**: 대용량 이미지 자산을 저장하기 위한 업계 표준.
    - **협업 환경 구축**: 로컬 파일을 압축/전달할 필요 없이, IAM **권한만 있으면 어디서든 데이터 접근 가능.**
    - **중앙 관리**: 모든 시각적 데이터를 한 곳에서 관리.

### **3. AWS DynamoDB: 비용 최적화를 위한 인덱스 및 상태 관리**

- **🔑 저장 대상 (What)**:
    - `product_id` (파티션 키)
    - S3에 저장된 각 이미지의 **파일명** (예: `detail` 폴더 내 `['abc.jpg', 'def.jpg']`)
    - 상품 카테고리 정보
    - **캡션 작업 완료 여부** 등 후속 작업을 위한 데이터 상태 플래그(Flag).
- **💡 선택 이유 (Why)**:
    - **비용 최적화**
        - **문제**: S3의 `List` API는 지속적으로 호출하기에 비용 부담이 큼.
        - **해결**: `product_id`로 DynamoDB를 조회(저비용)하여 필요한 모든 파일명을 얻음 -> 프로그램에서 완전한 S3 Key(`.../product_id/segment/abc.jpg`)를 조합 -> S3에 저렴한 `Get` API로 파일 직접 요청.
        - **결론**: 비싼 API 호출을 원천적으로 차단하는 아키텍처 구현.
    
    ### **비용 최적화를 위한 아키텍처 설계**
    
    S3만으로 특정 상품(`product_id`)에 연관된 모든 이미지를 가져오기 위해서는, 먼저 비용이 높은 `List` API를 호출하여 해당 상품 폴더 내의 모든 파일명을 알아낸 후, 다시 `Get` API를 호출해야 합니다. 저희는 **DynamoDB를 중간 인덱스로 활용하여 이 비효율적**인 과정을 근본적으로 개선했습니다.
    
    | 구분 (Category) | S3 단독 사용 시 (S3-Only Approach) | **DynamoDB + S3 연동 시 (권장 아키텍처)** |
    | --- | --- | --- |
    | **1. 키 탐색** | S3 `List` API 호출 (`/product_id/` 경로 스캔) | DynamoDB `Query` API 호출 (`product_id`로 조회) |
    | **2. 키 생성** | 반환된 결과로 S3 Key 목록 생성 | 반환된 파일명으로 S3 Key 목록 **직접 생성** |
    | **3. 파일 다운로드** | 생성된 Key로 S3 `Get` API 호출 | 생성된 Key로 S3 `Get` API 호출 |
    | **핵심** | **비싼 `List` API 호출이 필수적** | **`List` API 호출 없이 저렴한 `Query`로 대체** |
    
    **[정량적 비용 비교 (AWS 서울 리전 기준)]**
    
    - **S3 `List` 요청**: 1,000회당 $0.005
    - **S3 `Get` 요청**: 1,000회당 $0.0004
    - **DynamoDB 읽기 요청**: 100만 회(RRU)당 $0.325 (1 RRU = 최대 4KB)
    - **DynamoDB 쓰기 요청:** 100만 쓰기 요청 단위(WRU)당 **$1.625**
        - 1 WRU는 **최대 1KB**의 데이터를 쓰는 데 사용됩니다.
    
    > 시나리오: 10만 개의 상품 데이터를 후속 작업(캡션 등)에서 처리하는 경우
    > 
    > - **S3 단독**: 10만 번의 `List` API 호출 필요 → (100,000 / 1,000) * $0.005 = **$0.5**
    > - **DynamoDB 연동**: 10만 번의 `Query` API 호출 필요 (항목당 4KB 미만 가정) → (100,000 / 1,000,000) * $0.325 = **$0.0325**
    > 
    > **결론**: **단순히 파일 목록을 가져오는 과정에서부터 약 93% 이상의 비용 절감 효과**를 거둘 수 있습니다. `Get` 요청 비용은 양쪽 모두 동일하므로, 데이터 처리량이 많아질수록 이 비용 차이는 기하급수적으로 커집니다.
    > 
    
    - **상태 관리**: 각 데이터의 처리 상태(예: 캡션 완료/미완료)를 관리하기 용이.
    
    ### **기능적 확장성 확보**
    
    비용 외에도 DynamoDB는 S3 단독으로는 불가능한 필수적인 기능들을 제공합니다.
    
    - **고급 쿼리 및 필터링**: S3는 파일명의 접두사(prefix) 외에는 복잡한 조건 검색이 불가한 반면 DynamoDB의 기본 인덱스와 GIS 인덱스를 이용해서 "**캡션 작업이 아직 완료되지 않은(`status = 'pending'`) 모든 상품을 찾아줘" 와 같은 유연하고 강력한 쿼리**가 가능합니다.
    - **데이터 상태 추적**: 각 상품 데이터의 생명주기(Life-cycle)를 관리할 수 있습니다. `caption_status` 같은 속성을 두어 '작업 대기', '작업 중', '완료', '오류' 등의 상태를 기록하고 추적함으로써, **대규모 데이터 처리 파이프라인을 안정적으로 운영**할 수 있습니다.
    - **운영 효율성**: DynamoDB는 **사용한 만큼만 비용을 지불하는 완전 관리형 서버리스** 데이터베이스입니다. **별도의 서버 관리 없이 운영 부담을 최소화**할 수 있어, 개발 및 관리에 드는 리소스를 절약할 수 있습니다.
</aside>

### 4. 캡션 작업을 위한 작업 환경 구현

이미지 캡션 생성을 위해, **사전에 정의된 구조의 데이터셋을 구축하는 과정이 필수적**입니다. 이를 위해, 작업자가 비정형적인 이미지 데이터 속에서 필요한 정보를 효율적으로 선택하고 가공할 수 있도록 **Python**의 **`PySide6`** 라이브러리를 기반으로 한 데스크톱 GUI 어플리케이션을 개발했습니다.

본 어플리케이션은 **3단 패널(Three-Panel) 레이아웃**을 채택하여 사용자 편의성을 극대화했습니다. 사용자가 좌측 패널에서 작업할 상품을 선택하면, 중앙 패널에 S3로부터 다운로드한 해당 상품의 분할 이미지들이 표시됩니다. 작업자는 이 이미지들 중에서 과업의 요구사항(모델 정면샷, 제품 누끼샷 등)에 맞는 이미지를 선택하며, 그 결과는 우측 패널에 실시간으로 반영됩니다. 또한, 데이터 분할 오류나 정보 누락에 대응하기 위한 **이미지 이동, 잘라내기(Crop), 상태 변경(Pass)** 등 다양한 보조 기능을 탑재하여 데이터의 품질을 높였습니다. 모든 작업 내용은 최종적으로 **DynamoDB**에 업데이트되어, 후속 캡션 작업에 사용될 정형화된 데이터셋을 완성합니다.

### **4.1 어플리케이션의 주요 구성 요소 (3단 패널 UI)**

- **좌측 패널 (작업 대상 선택)**:
    - 사용자가 `main/sub category`를 선택하면, **DynamoDB**에서 해당 조건의 상품 ID 목록을 **페이지네이션(Pagination)**을 통해 20개씩 로드.
    - 선택된 상품들의 이미지와 `meta.json`을 **S3**에서 로컬 캐시 디렉토리로 다운로드.
- **중앙 패널 (이미지 뷰어 및 선택)**:
    - 좌측에서 선택된 상품의 이미지들을 폴더별(`segment`, `detail` 등)로 보여주는 뷰어.
    - 사용자는 이 곳에서 과업에 필요한 이미지를 선택.
- **우측 패널 (선택 결과 확인 및 완료)**:
    - 사용자가 선택한 이미지들이 실시간으로 표시되는 영역.
    - 최종적으로 **'작업 완료(Complete)'** 또는 **'패스(Pass)'** 버튼을 눌러 작업을 종료.

### **4.2 주요 작업 흐름 (Workflow)**

1. **데이터 로드**: 사용자가 카테고리 선택 시, DynamoDB에서 상품 목록을 가져와 로컬에 캐싱.
2. **이미지 할당**: 작업자는 특정 상품에 대해 아래 기준에 맞는 이미지를 중앙 패널에서 선택.
    - **필수 이미지 3종**: 특정 대표 색상의 ①모델 정면 착용샷, ②제품 정면 누끼샷, ③제품 후면 누끼샷.
    - **색상별 이미지**: 상품의 모든 색상에 대한 제품 정면 누끼샷.
3. **데이터 보정 (예외 처리)**:
    - 필요한 이미지가 없거나 잘못 분할된 경우, **'잘라내기(Crop)'** 기능으로 기존 이미지에서 새 이미지를 생성.
    - 사이즈 정보가 이미지 형태일 경우, 해당 이미지를 `text` 폴더로 이동.
4. **작업 완료**:
    - **Complete**: 선택된 이미지 정보(S3 key)와 수정사항을 **DynamoDB**에 업데이트하고, 상태를 `COMPLETED`로 변경.
    - **Pass**: 작업이 불가능한 데이터의 경우, 사유를 선택/기록하고 상태를 `PASS`로 변경.
    

### **4.3 어플리케이션 배포 및 버전 관리 (CI/CD)**

개발된 어플리케이션의 쉬운 배포와 체계적인 버전 관리를 위해 **`GitHub Actions`** 를 활용한 자동화 파이프라인을 구축했습니다.

- **자동 빌드 및 패키징**: 소스 코드가 GitHub에 푸시될 때마다 워크플로우가 자동으로 실행되어, **Windows와 macOS 환경 각각에 맞는 실행 파일**을 생성하고 이를 ZIP 파일로 압축합니다.
- **GitHub Releases를 통한 배포**: 성공적으로 빌드된 ZIP 파일은 프로젝트의 **GitHub Releases** 페이지에 새로운 버전으로 자동 업로드됩니다. 각 릴리즈에는 해당 버전에서 변경된 내역(새로운 기능, 버그 수정 등)을 상세히 기록하여 **체계적인 버전 관리(Versioning)**를 수행합니다.
- **효율적인 협업 환경**: 팀원들은 더 이상 로컬에서 직접 소스 코드를 받아 빌드할 필요가 없습니다. **본인의 운영체제에 맞는 ZIP 파일을 Releases 페이지에서 다운로드하고 압축을 풀기만 하면 즉시 프로그램을 사용할 수 있습니다. AWS IAM 자격 증명만 되어 있다면, 모든 팀원이 전 세계 어디서든 동일한 최신 버전의 도구로 작업을 수행할 수 있는 일관된 환경을 제공**합니다.

### **효율성 및 정확도를 높이는 핵심 기능**

- **로컬 캐싱(Local Caching)**: 한 번 다운로드한 이미지는 로컬 캐시에 저장, 앱 재시작 시 재다운로드를 방지하여 **S3 `Get` API 비용 절감 및 로딩 속도 향상**.

### 5. 캡션 작업에 쓸 데이터 생성

 5단계에서는 4단계에서 개발 및 배포한 GUI 어플리케이션을 활용하여, **LLM 기반의 캡션 생성을 위한 핵심 데이터셋을 구축하는 실질적인 작업**을 수행했습니다. 다수의 작업자는 GitHub Releases를 통해 최신 버전의 어플리케이션을 다운로드하여, 사전에 정의된 가이드라인에 따라 각 상품의 핵심 이미지(모델 착용샷, 정면/후면 누끼샷, 색상별 누끼샷)를 선택하고 할당했습니다. 이 과정을 통해, 각 상품 데이터는 **DynamoDB** 상에서 단순한 이미지 파일명 리스트에서 **'모델샷', '색상별 대표 이미지' 등 명확한 역할이 부여된 구조화된 정보**로 변환되었습니다. 작업이 완료된 데이터는 `COMPLETED` 상태로, 작업이 불가능한 데이터는 `PASS` 상태로 업데이트하여, 후속 LLM 모델이 사용할 데이터의 정합성과 품질을 확보했습니다.

- 4단계에서 정의된 워크플로우에 따라, 각 `product_id` 별로 필요한 이미지를 선택하고 역할을 할당했습니다.
- **상태 업데이트**: 작업이 완료된 상품은 **'Complete'** 버튼을, 작업이 불가능한 데이터는 **'Pass'** 버튼을 눌러 DynamoDB 상의 상태를 실시간으로 업데이트했습니다.

### **5.1 핵심 산출물 (Deliverables)**

이 단계의 핵심 산출물은 파일이 아닌, **정보가 풍부해진 DynamoDB 테이블**입니다.

- **구조화된 정보 추가**: 작업 전의 DynamoDB 아이템이 단순히 파일명 리스트만 가지고 있었다면, 작업 후에는 선택된 이미지를 저장

```json
"representative_assets": {
      "model" : "segment/0_1.jpg", 
      "front" : "segment/1_0.jpg",
      "back": "segment/1_1.jpg" ,
      "color_variant":["segment/1_0.jpg" , "segment/2_0.jpg"]
  }
 
```

- **상태 플래그 변경**:
    - `status` 속성이 '**PENDING**'에서 **'COMPLETED'** 또는 **'PASS'** 로 변경됩니다. 이는 다음 단계의 모델이 어떤 데이터를 학습에 사용해야 하는지를 알려주는 중요한 지표가 됩니다.
    

### 6. llm을 이용한 캡션 작업 및 추가 데이터 추출

5단계에서 구축한 정형 데이터셋을 기반으로, LLM을 활용하여 벡터 검색의 핵심이 될 풍부한 메타데이터와 캡션을 생성했습니다. **단일 LLM에 모든 과업을 맡기는 대신, 의류 분석, 색상 분류, 텍스트 추출(OCR)이라는 세 가지 명확한 역할을 가진 독립적인 LLM 에이전트 파이프라인을 설계**했습니다. 각 llm은 각 상황에 맞는 최적화된 프롬프트와 Pydantic 모델을 통해 정해진 구조의 결과만을 반환하도록 제어됩니다.

특히, `LangChain`을 활용하여 이 세 개의 LLM 호출을 **병렬(Parallel)으로 처리**함으로써, 전체 작업 시간을 단일 LLM 호출 시간과 유사한 4~5초 수준으로 단축했습니다. 또한, DynamoDB의 데이터를 페이지 단위로 **비동기(Asynchronous)** 처리하여 전체 데이터셋에 대한 캡션 생성 속도를 극대화했습니다. 모든 LLM의 입출력, 비용(토큰 수), 소요 시간은 `LangSmith`를 통해 실시간으로 모니터링하여 안정성을 확보했습니다. 최종적으로 LLM이 생성한 구조화된 데이터는 **MongoDB**에 저장하고, **DynamoDB**에는 '캡션 완료' 상태를 기록하여 전체 파이프라인을 완성했습니다.

### **6.1. 데이터 준비: LLM 입력을 위한 이미지 전처리**

LLM이 각 과업을 명확히 인식할 수 있도록, 입력 이미지를 세 종류의 합성 이미지로 가공했습니다.

1. **핵심 분석용 이미지**: `model`, `front`, `back` 이미지를 각각 512px로 리사이즈 후, **수평으로 이어 붙여** 하나의 이미지로 합성. Base64로 인코딩하여 전달.
2. **색상 분석용 이미지**: 색상별 누끼 이미지를 각각 224px로 리사이즈 후, **수평으로 이어 붙여** 합성. 각 이미지 좌측 상단에 숫자 인덱스를 표기하여 LLM이 결과를 명확히 매칭하도록 유도.
3. **텍스트 분석용 이미지**: `text` 폴더 내의 모든 이미지를 512px로 리사이즈 후, **수직으로 이어 붙여** 합성. (해당 이미지가 없는 경우 이 과정은 생략)

### **6.2 LLM 기반 병렬 처리 파이프라인 설계**

"한 명의 만능 전문가"가 아닌 **"세 명의 전문 에이전트"가 협업하는 방식으로 파이프라인을 설계**하여, 각 과업의 정확도와 효율을 높였습니다.

| LLM 에이전트 | 입력 데이터 (Input Data) | 주요 과업 (Main Task) | 산출물 (Output) |
| --- | --- | --- | --- |
| **① 의류 분석 전문가** | 핵심 분석용 합성 이미지 | 의류의 상세 속성 및 스타일 분석 | 검색 필터링 및 태깅에 사용될 해당 의류의 속성 정보(의류의 기장, 패턴, 스타일, TPO, 핏) , 벡터 임베딩에 사용될 다양한 관점의 자연어(이미지 묘사, 디자인, 스타일, TPO에 대한 설명문구) |
| **② 색상 분류 전문가** | 색상 분석용 합성 이미지 | 색상 분류 및 속성(HEX 등) 추출 | 각 색상별 이름, HEX 코드, 명도, 채도 |
| **③ 텍스트 추출 전문가** | 텍스트 분석용 합성 이미지 | OCR 및 핵심 정보 추출 (사이즈 표 등) | 의류 사이즈표(JSON 형식), 소재 등 유의미한 텍스트 |
- **정형화된 결과 보장**: 모든 에이전트의 결과물은 **사전에 정의된 Pydantic 모델에 맞춰 JSON 형식으로 반환**되도록 하여, 데이터의 일관성과 정합성을 확보했습니다.

### 각 모델별 정형화된 모델 구조

### **1. 의류 분석 전문가 출력 모델: `DeepCaptioningTopOutput`**

가장 복잡한 분석을 수행하는 이 전문가는 의류의 모든 속성을 두 개의 큰 갈래로 나누어 출력합니다.

- **`structured_attributes` (구조화된 속성)**: **검색 필터링 및 태깅에 직접 사용될 객관적/주관적 속성 정보**입니다.
    - **`common`**: `sleeve_length`(소매 길이), `neckline`(넥라인) 등 의류의 공통적인 기본 속성.
    - **`front` / `back`**: `pattern`(패턴), `closures_and_embellishments`(여밈/장식) 등 정면과 후면에서 보이는 고유한 디자인 요소.
    - **`subjective`**: `fit`(핏), `style_tags`(스타일), `tpo_tags`(TPO) 등 모델의 주관적 판단이 들어가는 태그.
    - **핵심**: 모든 속성은 미리 정의된 **`Enum` 타입**(예: `Neckline.ROUND`, `StyleTag.CASUAL`) 내에서만 선택되도록 하여, 데이터의 일관성을 강제합니다.
- **`image_captions` (이미지 캡션)**: **벡터 임베딩에 사용될, 다양한 관점의 서술형 텍스트**입니다.
    - `front_text_specific`, `back_text_specific`: 각 이미지에 대한 상세 묘사.
    - `design_details_description`, `style_description`, `tpo_context_description`: 디자인, 스타일, TPO 등 특정 주제에 대한 심층 설명.
    - `comprehensive_description`: 위의 모든 정보를 종합한 완전한 최종 설명문.

### **나. 색상 분류 전문가 출력 모델: `SimpleAttributeOutput`**

색상 정보에만 집중하여, 이미지에 나타난 각 색상에 대한 상세 정보를 리스트 형태로 출력합니다.

- **`color_info` (색상 정보 리스트)**: 각 색상 정보(`ColorInfo`)는 아래 세 가지 요소로 구성됩니다.
    - **`name`**: `PrimaryColor` Enum으로 정의된 대표 색상명 (예: "레드", "블루").
    - **`hex`**: `^#[0-9A-Fa-f]{6}$` 정규식으로 검증되는 6자리 HEX 코드.
    - **`attributes`**: `Brightness`(명도), `Saturation`(채도) Enum으로 정의된 색상의 세부 속성.

### **다. 텍스트 추출 전문가 출력 모델: `TextImageOCROutput` (조건부 모델)**

이 전문가는 **입력 컨텍스트에 따라 다른 Pydantic 모델을 동적으로 선택**하여 출력을 생성합니다.

- **`size_info`가 이미 크롤링된 경우 (`TextImageOCROutput_NoSize` 모델 사용)**:
    - `material_info`(소재), `care_info`(세탁법), `product_description`(상품설명) 등 텍스트 정보만 추출.
- **`size_info`가 누락된 경우 (`TextImageOCROutput_Full` 모델 사용)**:
    - 위의 정보와 더불어, 이미지 속 표나 그래프에서 **`size_info`(상세 사이즈 정보)**를 반드시 추출하여 정해진 JSON 형식으로 반환하도록 강제합니다.

이처럼 정교하게 설계된 Pydantic 모델들은 LLM이라는 강력하지만 예측하기 어려운 도구를, 우리 시스템이 원하는 방향으로만 작동하도록 하는 '안전장치'이자 '설계도'의 역할을 수행합니다.

### **6.3. 실행 최적화 및 모니터링**

- **실행 속도 최적화**:
    - **병렬 처리(Parallelism)**: `LangChain`을 이용해 독립적인 3개의 LLM 호출을 동시에 실행, 순차 실행 시 10초 이상 소요될 작업을 **단일 작업의 최대 소요 시간인 4~5초 내에 완료**했습니다.
    - **비동기 처리(Asynchronicity)**: DynamoDB에서 페이지 단위로 가져온 여러 상품 데이터를 **비동기적으로 처리**하여, 전체 처리량(Throughput)을 극대화했습니다.
- **모니터링**: `LangSmith`를 연동하여 모든 LLM Chain의 **실행 과정, 입/출력 데이터, 토큰 사용량, 비용, 지연 시간(Latency)** 등을 추적하여 디버깅 및 성능 관리를 용이하게 했습니다.

### **6.4. 최종 데이터 저장 및 상태 관리**

- **MongoDB**: LLM이 생성한 모든 구조화된 메타데이터(스타일, 색상, 사이즈 정보, 캡션 등)는 해당 상품의 마스터 데이터가 있는 MongoDB에 업데이트하여 정보를 풍부하게 만듭니다.
- **DynamoDB**: 작업이 완료된 상품의 `caption_status`를 `COMPLETED`로 업데이트합니다. 이를 통해, '작업은 완료됐지만 캡션은 생성되지 않은' 데이터만 효율적으로 필터링하여 중복 작업을 방지합니다.

### 7. 임베딩 작업

7단계에서는 6단계에서 생성된 텍스트 캡션들을 검색 모델이 이해할 수 있는 **고차원 벡터(Vector)**로 변환하는 임베딩(Embedding) 작업을 수행했습니다. 이를 위해, 한국어 텍스트에 높은 성능을 보이는 **`jina-embeddings-v3`** 모델을 사용하여 각 캡션을 **1024차원의 벡터**로 변환했습니다. 대량의 캡션을 효율적이고 안정적으로 처리하기 위해, 단순 비동기 처리를 넘어 **`Queue`와 `Semaphore`를 활용한 API 호출 제어 로직을 구현**했습니다. 이 방식을 통해 임베딩 서버의 API 속도 제한(Rate Limit)에 유연하게 대응하고 시스템의 부하를 조절하며 최대 처리량을 유지할 수 있었습니다. 최종적으로 생성된 벡터 데이터는 원본 상품 정보와 함께 **MongoDB**에 저장하여, 벡터 검색을 위한 데이터 준비를 완료했습니다.

### **7.1. 주요 작업 과정 및 최적화**

1. **데이터 로딩**: **MongoDB**에서 캡션 생성이 완료된(`caption_status: 'COMPLETED'`) 상품들의 캡션 텍스트를 불러옵니다.
2. **임베딩 API 호출**: **`jina-embeddings-v3`** 모델 API를 호출하여 각 캡션을 1024차원 벡터로 변환합니다.
3. **안정적인 비동기 처리**:
    - `asyncio`를 기반으로 전체 프로세스를 비동기적으로 설계했습니다.
    - 처리해야 할 모든 캡션을 **`Queue`** 에 순서대로 추가합니다.
    - **`Semaphore`** 를 사용해 동시에 API를 호출하는 동시 작업(Concurrent task)의 개수를 제한합니다. 이는 API 서버에 과도한 요청을 보내 발생하는 오류를 방지하고, 안정적인 처리 속도를 보장하는 핵심적인 제어 장치 역할을 합니다.
4. **데이터 저장**: 변환된 벡터는 **MongoDB**의 해당 상품 다큐먼트에 `caption_vector` 와 같은 새로운 필드를 추가하여 저장합니다.

### 8. 벡터 DB 및 마이그레이션

앞선 과정들을 통해 완성된 데이터(메타데이터, 캡션, 벡터)를 실제 벡터 검색 서비스를 위해 클라우드 데이터베이스인 **MongoDB Atlas**로 이전하는 작업을 수행했습니다. 데이터 이전 후, mongodb Atlas가 제공하는 **Vector Search 기능을 활용하여 검색 인덱스를 생성**했습니다. 텍스트 임베딩의 의미적 유사도 측정에 널리 사용되는 **코사인 유사도(Cosine Similarity)**를 기준으로 인덱스를 설정했습니다. 

**향후 계획: PostgreSQL 마이그레이션** 

> 현재는 MongoDB Atlas를 통해 벡터 검색 기능을 구현했지만, 향후 시스템 고도화를 위해 AWS의 동일 VPC 환경 내에 있는 PostgreSQL로 마이그레이션을 계획하고 있습니다. 이는 서비스의 다른 구성 요소들과 데이터베이스를 동일한 네트워크 환경에 배치함으로써, 네트워크 지연 시간(Latency)을 최소화하고 아키텍처를 단순화하기 위함입니다. 마이그레이션을 위한 ERD(개체-관계 다이어그램) 설계는 이미 완료된 상태이며, PostgreSQL의 벡터 검색 확장 기능인 pgvector를 활용할 예정입니다.

### **벡터 검색 기반 의류 추천 시스템을 위한 End-to-End 데이터 파이프라인 구축**

본 프로젝트의 목표는 벡터 검색 기반의 고도화된 의류 추천 서비스를 구현하기 위해, 웹상의 비정형 데이터를 수집, 가공하여 최종적으로 **검색 가능한 벡터 데이터셋으로 변환하는 확장 가능하고 안정적인 End-to-End 데이터 파이프라인을 설계 및 구축하는 것**입니다. 이 파이프라인은 데이터의 수집부터 정제, 그리고 최종 배포에 이르는 전 과정을 자동화하고 최적화하는 데 중점을 두었습니다.

### **1~2 단계 : 데이터 수집 및 전처리 (Collection & Preprocessing)**

파이프라인의 시작은 **Selenium**과 **BeautifulSoup**을 활용한 크롤링 프로세스입니다. 무신사 의류 사이트로 부터 Selenium으로 동적 페이지(Infinite Scroll)를 제어하여 대상 상품의 URL 리스트를 확보한 후, 이 리스트를 기반으로 각 상세 페이지의 정적 데이터를 안정적으로 수집했습니다.

수집된 데이터의 가장 큰 난관은 여러 정보(제품, 모델, 텍스트)가 혼합된 긴 복합 이미지(Composite Image)였습니다. 이를 해결하기 위해 **OpenCV** 기반의 커스텀 이미지 분할 알고리즘을 개발했습니다. 이 알고리즘은 단순히 흰색 영역을 찾는 것을 넘어, **행(row)별 픽셀 평균, 특정 임계치 이하 픽셀 수, 그리고 인접 행과의 픽셀 값 차이**라는 3가지 조건을 복합적으로 사용하여, **텍스트 블록이나 흰색 의류를 분리 경계로 오인하는 경우를 최소화하고 분할의 정확도를 높였**습니다.

### **3-5. 데이터 지속화 및 정형화 파이프라인 (Persistence & Annotation Pipeline)**

데이터 저장은 **목적 기반 다중 저장소(Polyglot Persistence)** 전략을 채택했습니다. MongoDB는 비정형 메타데이터, AWS S3는 이미지 에셋, 그리고 **AWS DynamoDB**는 비용 최적화를 위한 핵심 인덱싱 레이어로 활용하여 고비용 `ListObjects` API 호출을 회피하는 아키텍처를 구현했습니다.

데이터 정형화를 위해 **PySide6** 기반의 데스크톱 GUI 어플리케이션을 개발하고, **GitHub Actions**를 통해 CI/CD 파이프라인을 구축하여 Windows와 macOS용으로 자동 배포했습니다.

어플리케이션의 핵심 과업은 작업자가 각 상품에 대해 **필수 이미지 3종(모델 착용샷, 제품 정면/후면 누끼샷)을 특정**하고, 상품이 가진 **모든 색상에 대한 대표 이미지(정면 누끼샷)를 선택**하는 것입니다. 이 작업의 결과로, DynamoDB에 사용자가 선택한 이미지에 대한 정보가 반영이되며 상태 플래그가 `COMPLETED`로 업데이트됩니다. 이는 후속 LLM이 컨텍스트를 정확히 인지하고 분석할 수 있도록 하는 핵심적인 정형화 과정입니다.

### **6-7. 데이터 강화 및 벡터화 (Enrichment & Vectorization)**

정형화된 데이터를 심층 분석하기 위해 **LangChain** 기반의 모듈형 LLM 파이프라인을 구축했습니다. 세 가지 명확한 역할을 가진 독립적인 LLM 에이전트가 병렬로 작업을 수행하며, 각 에이전트의 역할은 다음과 같습니다.

- **의류 분석 전문가**: 선택된 핵심 이미지 3종(모델 착용샷, 제품 정면/후면 누끼샷) 을 바탕으로 의류의 **스타일, 핏, TPO, 디자인 디테일을 종합적으로 분석**하고 다각적인 캡션을 생성합니다.
- **색상 분류 전문가**: 색상별 이미지를 분석하여 미리 정의된 **카테고리(대표색, 명도, 채도)로 분류**하고 정확한 **HEX 코드를 추출**합니다.
- **텍스트 추출 전문가**: 이미지 속 텍스트를 OCR로 인식하여 **사이즈 표, 소재 등 필요한 정보만 선별적으로 구조화**하여 추출합니다.

모든 LLM의 출력은 **Pydantic 모델**을 통해 엄격한 스키마를 강제하며, **LangSmith**를 통해 전 과정이 추적 및 모니터링됩니다. 이렇게 생성된 캡션 데이터는 **`jina-embeddings-v3`** 모델을 통해 **1024차원의 벡터**로 변환되며, 이 과정은 **`asyncio` 기반의 Queue와 Semaphore**를 통해 안정적이고 효율적으로 처리됩니다.

### **8단계 : 벡터 DB 배포 및 서비스 준비 (Deployment & Indexing)**

최종적으로 모든 메타데이터와 벡터 데이터는 **MongoDB Atlas**로 이전됩니다. 실시간 검색 서비스를 위해, Atlas의 Vector Search 기능을 활용하여 **1024차원 `caption_vector` 필드**에 대해 **코사인 유사도** 기반의 **ANN(근사 최근접 이웃) 인덱스**를 생성했습니다.

향후 계획으로는 AWS 내 타 서비스와의 네트워크 지연 시간 최소화를 위해, 현재 아키텍처를 **PostgreSQL**과 **`pgvector`** 확장 기능을 사용하는 환경으로 마이그레이션하는 것을 고려하고 있으며, 이를 위한 ERD 설계는 완료된 상태입니다.

## 쿼리 분석 LLM 개발

사용자의 자연어(Natural Language) 검색 쿼리는 비정형적이고 다양하지만, 데이터베이스에 저장된 의류 정보는 정형화되어 있어 의미적 간극이 발생합니다. 이 문제를 해결하고 검색 정확도를 극대화하기 위해, **사용자의 의도를 파악하여 데이터베이스가 이해할 수 있는 구조화된 명령으로 변환하는 LLM 파이프라인을 설계 및 개발**

개발 결과, 평균 1.7~2.0초 내에 사용자의 복합적인 쿼리까지 실시간으로 분석하여 검색 결과를 반환하는 안정적인 시스템을 구축했습니다.

### 1. 주요 기능 및 아키텍처

### 가. 이중 호출(2-Call) 아키텍처 채택

쿼리 분석의 정확도와 속도를 최적화하기 위해 단일 호출(1-Call)과 이중 호출(2-Call) 두 가지 아키텍처를 비교 테스트했습니다. 테스트 결과, 정확도를 최우선으로 고려하여 **2-Call 아키텍처**를 최종 채택했습니다.

- **1-Call 방식**: 단일 LLM 호출로 쿼리 분해 및 필터 추출을 동시에 수행.
- **2-Call 방식**: LLM 호출을 2단계로 분리하여 각 단계의 과업을 명확히 함.

**[아키텍처 결정 사유]**
1-Call 방식은 약 1.2초의 빠른 속도를 보였으나, 색상과 같은 특정 속성 추출에서 정확도가 저하되는 경우가 있었습니다. 반면 2-Call 방식은 약 1.7~2.0초로 소폭의 지연 시간이 발생하지만, **각 단계의 역할이 명확하여 월등히 높은 분석 정확도**를 보였습니다. 추천 품질에 직결되는 정확도를 확보하는 것이 더 중요하다고 판단하여 2-Call 방식을 채택했습니다.

**[2-Call 처리 흐름]**

1. **1단계: 아이템 식별 및 문맥 추출**
    - 사용자 쿼리에서 '상의', '하의' 등 분석 대상 아이템을 식별하고, 관련된 원본 쿼리 조각을 분리합니다. (`InitialAnalysis` 모델 사용)
    - "출근할 때 입을"과 같이 모든 아이템에 적용되는 **공통 문맥(Common Context)을 별도로 추출**합니다.
2. **2단계: 상세 분석 및 쿼리 재구성**
    - 1단계에서 식별된 각 아이템에 대해 **독립적이고 병렬적으로** 상세 분석을 수행합니다.
    - 미리 정의된 `TopFilter`, `BottomFilter` Pydantic 모델을 사용하여 색상, 핏, 스타일 등의 속성을 구조화된 필터로 추출합니다.
    - 추출된 필터와 문맥을 조합하여 벡터 검색에 최적화된 **'재구성된 쿼리(Rewritten Query)'**를 최종 생성합니다.

### 나. 비동기 및 병렬 처리를 통한 성능 최적화

2-Call 아키텍처의 응답 시간을 최적화하기 위해 비동기 및 병렬 처리 방식을 도입했습니다. 사용자가 "청바지와 흰색 티셔츠"처럼 여러 아이템을 동시에 검색할 경우, 각 아이템에 대한 2단계 분석(상세 분석 및 쿼리 재구성) 프로세스가 **병렬로 동시에 실행**됩니다. 이를 통해 분석할 아이템의 수와 관계없이 전체 응답 시간을 약 2초 내외로 유지하는 효율적인 시스템을 구현했습니다.

## **전체 동작  파이프라인 flow-chart(사용자 검색 처리)**

이 단계는 실제 사용자의 검색 요청이 들어왔을 때, 준비된 DB를 활용하여 최적의 결과를 실시간으로 반환하는 과정입니다.

### **1단계: API 요청 접수**

- 사용자가 서비스를 통해 검색을 요청하면, 메인 **스프링(Spring) 서버**는 해당 요청을 AI 기능을 담당하는 **FastAPI 서버**로 전달합니다.

### **2단계: 쿼리 분석 (Query Analysis LLM)**

- FastAPI 서버는 전달받은 사용자 쿼리를 **'쿼리 분석 LLM'**에 입력합니다.
- 앞서 정의한 **2-Call 아키텍처**가 작동하여, 쿼리에 담긴 의도를 분석하고 아래 두 가지 핵심 정보를 추출합니다.
    1. **구조화된 필터**: DB에서 검색 대상을 좁히기 위한 속성 (`{color: "블랙", sub_category: "후드티셔츠"}` 등)
    2. **재구성된 쿼리 (Rewritten Query)**: 의미적으로 더 풍부해진, 벡터 검색에 사용될 자연어 쿼리

### **3단계: 필터링 및 벡터 검색**

- AI 서버는 먼저 **(1) 구조화된 필터**를 사용하여 MongoDB Atlas에서 검색 대상을 1차적으로 좁힙니다. (예: '블랙 색상의 후드티셔츠만 검색')
- 그다음, 1차로 필터링된 상품들 내에서 **(2) 재구성된 쿼리**를 사용하여 벡터 검색을 수행하고, 의미적으로 가장 유사한 Top-K개의 상품 정보를 반환받습니다.

### **4단계: 응답 데이터 생성**

- DB로부터 반환된 상품 정보(`product_id` 등)를 기반으로, **AWS S3**에 저장된 실제 이미지에 접근할 수 있는 **파일 키(File Key)**를 생성합니다.
- 생성된 파일 키를 이용하여 일정 시간 동안만 유효한 **보안 다운로드 URL(Pre-signed URL)**을 발급받습니다.

### **5단계: 최종 결과 반환**

- FastAPI 서버는 상품 정보와 보안 다운로드 URL을 포함한 최종 결과를 JSON 형태로 가공하여 스프링 서버에 반환합니다.
- 스프링 서버는 이 결과를 받아 사용자에게 추천 의류 목록을 보여주며 전체 과정을 완료합니다.

### 향후 보안사항

1. langgraph를 이용하여 사용자의 행위에 대해 동적으로 기능이 동작하도록 정의 
2. llm 비용및 응답 속도를 측정하여 병목지점 개선
3. 여러 벡터 필드에 대한 하이브리드 서치 도입하여 보다 유사한 결과가 나오도록 정의
4. 쿼리 분석 세분화
