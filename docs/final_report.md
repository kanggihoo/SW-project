## 1. LangGraph를 활용한 동적 상황 대응 아키텍처

저희 시스템의 가장 큰 기술적 특징은 **사용자의 모든 행동과 대화의 흐름에 실시간으로 반응하는 동적인 그래프 구조를 `LangGraph`로 구현**했다는 점입니다. 이는 미리 정해진 순서대로만 동작하는 일반적인 프로그램과 달리, 대화의 맥락에 따라 스스로 최적의 경로를 찾아가는 지능형 에이전트를 구현하는 핵심 기술입니다.

이 동적 아키텍처는 **State(상태)**, **Checkpointing(영속화)**, **Router(분기)**라는 세 가지 핵심 요소로 이루어집니다.

### 가. 핵심 구성요소 1: 단일 공유 상태(State)

그래프의 **모든 노드(기능)는 State라는 하나의 중앙 공유 메모리를 통해 모든 정보를 공유하며**, 다음과 같은 모든 맥락을 기억하고 실시간으로 업데이트합니다.

```python
 class State(TypedDict):
        # --- 전체 공유 상태 ---
        messages: Annotated[list[BaseMessage], add_messages]
        user_message: str
        intent: str
        product_id: str
        # ... (기타 상태)

        # --- 정보 수집/업데이트 관련 ---
        cloth_search: ClothSearch
        is_info_gathering_complete: bool
        last_updated_fields: list[str]

        # --- 코디 검색 서브그래프 관련 ---
        cache_cyclable: bool
        experts_to_run: list[str]
        current_expert: str
        expert_opinions: dict[str, str]
        expert_search_cache: dict[str, dict[str, list[str]]]
        expert_offsets: dict[str, int]
        shown_in_product_ids: set[str]
```

- 주요 상태 설명
    - `messages`: 전체 대화 기록을 관리합니다.
    - `intent`: `direct_search`, `info_qa` 등 분류된 사용자 의도를 저장
    - `cloth_search`: 검색에 필요한 조건(TPO, 색상, 스타일)을 담는 Pydantic 모델
    - `is_info_gathering_complete`: 검색 조건 수집 완료 여부를 나타내며, `True`가 되어야 검색 서브그래프가 실행
    - `last_updated_fields`: 사용자의 조건 변경을 감지하거나(`['style']`), 캐시 사용을 지시(`['__SHOW_CACHED__']`)하는 플래그
    - `expert_search_cache`: 전문가별로 검색된 상의(`TOP`), 하의(`BOTTOM`) 상품 ID 리스트를 저장하는 캐시로, 빠른 피드백의 핵심입니다.

### 나. 상태 영속화 (Checkpointing): 대화의 연속성 보장

본 시스템은 `LangGraph`의 **체크포인팅(Checkpointing) 기능**을 통해, 단발성이 아닌 **연속적인 대화(Multi-turn Conversation)**를 완벽하게 지원합니다.

매 상호작용이 끝날 때마다, `LangGraph`는 위에서 정의된 `State` 객체 전체를 스냅샷으로 만들어 **별도의 데이터베이스(AWS RDS PostgreSQL)에 실시간으로 저장**합니다.

1. **맥락을 기억하는 대화**: 사용자가 "방금 보여준 것 중에 첫 번째 거 다시 보여줘"라고 질문해도, 시스템은 DB에서 이전 `State`를 불러와 대화의 전체 맥락을 완벽하게 이해하고 정확한 답변을 할 수 있습니다.
2. **대화 이어가기**: 사용자가 브라우저를 닫았다가 다시 접속하더라도, 동일한 `thread_id`를 사용하는 한 DB에 저장된 마지막 대화 상태를 복원하여 중단된 지점부터 대화를 자연스럽게 이어나갈 수 있습니다.

### 다. 핵심 구성요소 2: 조건부 엣지(Router) - "상황에 따른 분기점"

그래프가 동적으로 움직일 수 있는 비결은 바로 **조건부 엣지**, 즉 **라우터(Router)**에 있습니다. **라우터는 `State`에 저장된 현재까지의 맥락(조건)을 확인하고, 다음에 실행될 노드(기능)를 실시간으로 결정하는 분기점**입니다.

시스템은 사용자의 모든 입력과 UI 인터랙션을 '조건'으로 인지하며, 라우터는 이 조건에 맞춰 스스로 작업 흐름을 재구성합니다.

### 라. State와 Router를 활용한 동적 흐름 (시나리오별 동작)

이 두 가지 구성요소가 실제 시나리오에서 어떻게 유기적으로 동작하는지는 다음과 같습니다.

**1) 초기 진입 분기 (Master Router)**

사용자의 입력이 들어오면, 그래프는 가장 먼저 `master_router`를 통해 `State`의 초기 값을 확인하고 어디로 가야 할지 결정합니다.

- **시나리오 1: 특정 상품에 대한 질문 (product_id 제공)**
사용자가 UI에서 특정 상품 이미지를 클릭하면 `product_id`가 `State`에 포함됩니다. `master_router`는 `product_id`가 존재하는 것을 확인하고, 일반 검색 흐름을 건너뛰어 즉시 **product_info_agent(상품 정보 조회)**로 작업을 넘깁니다.
- **시나리오 2: 미리 정의된 템플릿 클릭**
사용자가 "캐주얼 스타일 추천해줘" 같은 버튼(템플릿)을 클릭하면 `is_predefined_template` 상태가 True가 됩니다. `master_router`는 이를 인지하고, 복잡한 의도 분석을 생략한 채 곧바로 `prepare_template_search_node`를 거쳐 **search_subgraph(검색 서브그래프)**로 진입합니다.
- **시나리오 3: 일반 텍스트 검색**
위 두 경우가 아닌 일반 텍스트("데이트 때 입을 옷 찾아줘")가 입력되면, `master_router`는 그래프를 표준 절차인 **intent_classify_node(의도 분류 노드)**로 이동시켜 사용자의 숨은 의도를 파악하는 작업부터 시작합니다.

**2) 의도 기반 후속 분기**

시나리오 3처럼 일반 텍스트가 입력된 경우, 그래프는 내부의 라우터들을 통해 더 세밀하게 경로를 결정합니다.

- **의도 분류 및 경로 결정**: `intent_classify_node`는 사용자의 메시지를 분석하여 `intent` 상태를 `direct_search`, `search_refinement`, `chatbot` 등으로 결정합니다. 바로 다음 라우터인 `route_after_classification`은 이 `intent` 값을 확인하고 다음에 실행할 노드를 결정합니다.
    - `intent`가 `direct_search`이면 → `information_gathering_node`로 엣지를 연결하여 정보 수집을 시작합니다.
    - `intent`가 `search_refinement`이면 → `information_update_node`로 엣지를 연결하여 기존 검색 조건을 수정합니다.
    - `intent`가 `chatbot`이면 → `chatbot_node`로 엣지를 연결하여 일상적인 대화를 수행합니다.
- **정보 수집 완료 후 분기**: `information_gathering_node`가 모든 필수 정보(TPO, 스타일, 색상)를 수집하여 `is_info_gathering_complete` 상태를 True로 바꾸면, `route_after_gathering` 라우터는 이를 확인하고 드디어 **search_subgraph**로 향하는 엣지를 선택하여 실제 검색을 시작합니다. (정보가 부족하다면 END로 이동하여 사용자 추가 입력을 대기)

## 주요 노드 설명

### 가. `intent_classify_node`:

- **역할**: 사용자의 모든 발화 뒤에 숨겨진 **핵심 의도(Intent)**를 파악하여, 다음에 어떤 작업을 수행해야 할지 결정하는 가장 첫 번째 관문입니다.
- **동작 방식**:
    1. **1단계 (빠른 분류)**: 먼저 사용자의 최신 메시지만으로 '검색', '정보 질문', '일상 대화' 등 6가지 의도 중 하나로 빠르게 분류합니다.
    2. **2단계 (심층 분류)**: 만약 1단계에서 의도가 "불명확(`unclear`)"하다고 판단되면, 이 노드는 대화의 전체 맥락을 파악하기 위해 이전 대화 기록까지 포함하여 더 깊이 있게 재분류를 시도합니다.
- **중요성**: 이 노드가 없다면, 시스템은 사용자가 "오늘 날씨 좋네요"라고 말했을 때와 "데이트룩 찾아줘"라고 말했을 때를 구분하지 못하고 모든 입력을 검색으로 처리하려 할 것입니다. `intent_classify_node`는 사용자의 의도에 맞는 최적의 경험(대화, 정보 제공, 검색)을 제공하기 위한 첫 단추를 꿰는 핵심적인 역할을 합니다.

### 나. `information_gathering_node`:

- **역할**: 사용자의 의도가 '검색'으로 파악되었을 때, 성공적인 검색에 필수적인 정보(TPO, 스타일, 색상)를 수집하는 역할을 합니다.
- **동작 방식**:
    1. **정보 추출**: 사용자의 메시지("주말 데이트에 입을 캐주얼한 옷")에서 `extraction_prompt`를 이용해 `tpo: '데이트'`, `style: '캐주얼'`과 같은 구조화된 정보를 추출하여 `State`의 `cloth_search` 필드를 채웁니다.
    2. **되묻기**: 만약 '색상' 정보가 누락되었다면, 이 노드는 `generation_prompt`를 사용하여 "주말 데이트에 입을 캐주얼한 스타일을 찾으시는군요! 혹시 선호하는 색상이 있으신가요?"와 같이 부족한 정보를 자연스럽게 물어보는 질문을 생성합니다.
- **중요성**: 이 노드는 사용자의 모호한 요구사항을 명확한 검색 조건으로 구체화하는 핵심적인 단계입니다. 이 과정이 없다면, `search_subgraph`는 무엇을 검색해야 할지 알 수 없어 제대로 동작할 수 없습니다.

### 다. `information_update_node`: 사용자의 피드백을 반영하는 조율사

- **역할**: 이미 검색이 한 번 이상 진행된 상태에서, 사용자의 추가적인 요구사항("청바지 말고 면바지로 보여줘")을 반영하여 검색 조건을 수정노드
- **동작 방식**:
    1. `update_prompt`를 사용하여 사용자의 피드백을 해석하고, `State`의 `cloth_search`를 새로운 조건(예: `style: '면바지'`)으로 업데이트합니다.
    2. **가장 중요한 역할**로, 새로운 검색을 위해 기존의 검색 결과가 저장된 **`expert_search_cache`를 초기화**합니다. 이 초기화 작업이 바로 `search_subgraph`가 '캐시 검색'이 아닌 '신규 검색'을 다시 시작하도록 만드는 신호탄이 됩니다.
- **중요성**: 사용자와의 연속적인 상호작용을 통해 추천 결과의 만족도를 점진적으로 높여나가는, 대화형 추천 시스템의 핵심적인 기능을 담당합니다.

### 마. `chatbot_node`: 대화를 부드럽게 만드는 윤활유

- **역할**: 사용자가 의류와 관련 없는 일상적인 대화를 시도할 때, 자연스럽게 응대하며 대화의 흐름이 끊기지 않도록 하는 '윤활유' 같은 역할을 합니다.
- **동작 방식**: "오늘 너무 덥다"와 같은 메시지에 "정말 덥네요! 이런 날씨에 입기 좋은 시원한 옷을 찾아드릴까요?"처럼, 사용자의 말에 공감하면서도 자연스럽게 본래의 목적인 의류 추천으로 대화를 유도합니다.
- **중요성**: 이 노드가 없다면 시스템은 사용자의 모든 입력을 기능적으로만 처리하려 하여 딱딱하고 비인간적인 느낌을 줄 수 있습니다. `chatbot_node`는 시스템에 인간적인 면모를 부여하여 사용자에게 훨씬 더 긍정적인 대화 경험을 제공합니다.

### 사. `info_qa_node`

- 역할 : 패션 관련 정보 질문에 답변합니다.
- 해당 노드에는 내부에 있는 llm이 사용자 요청에 대해 거짓된 정보를 응답하지 않도록 웹 검색 도구를 이용하여 정확하고 최신정보를 가져와서 응답할 수 있도록 동작

## 2. Search Subgraph: 'State'를 활용한 '깊이'와 '속도'의 조화

`search_subgraph`는 `1. 아키텍처` 섹션에서 정의된 `State` 객체를 적극적으로 활용하여 코디를 추천하는 핵심 엔진입니다. 이 서브그래프의 목표는 **정확하고 깊이 있는 최초 검색**과 **신속하고 효율적인 추가 탐색**이라는 두 가지 목표를 동시에 달성하는 것입니다.

### 가. 주요 동작 방식: '신규 검색' vs '캐시 검색'

서브그래프는 `State`의 `last_updated_fields` 플래그를 확인하여 두 가지 모드 중 하나로 동작합니다.

1. **신규 검색 (Vector Search)**: 사용자가 처음 검색하거나 "청바지 말고 면바지로"처럼 조건을 변경(`last_updated_fields`에 'style' 등 포함)했을 때 실행됩니다. LLM 분석과 벡터 검색을 모두 사용하여 가장 정확한 결과를 찾습니다.
2. **캐시 검색 (Cached Search)**: 사용자가 "다른 거 보여줘"처럼 조건 변경 없이 추가 결과를 원할 때(`last_updated_fields`가 `['__SHOW_CACHED__']`일 때) 실행됩니다. 비용과 시간이 드는 LLM 분석 및 벡터 검색을 **건너뛰고**, `State`에 저장된 캐시를 사용해 즉각적인 피드백을 제공합니다.

### 나. 신규 검색 (Deep Analysis) 과정

1. **쿼리 분석**: `information_gathering_node`가 사용자의 메시지("주말 데이트에 입을 캐주얼한 옷")를 분석하여 `State.cloth_search`에 `tpo: '데이트'`, `style: '캐주얼'`과 같은 구조화된 필터를 저장합니다.
2. **전문가 의견 생성**: `search_subgraph` 내의 3명 전문가(LLM)가 `State`의 정보와 원본 메시지를 바탕으로 "데이트에 어울리는 화사한 색감"처럼 벡터 검색에 최적화된 **새로운 검색어(의견)를 생성**합니다.
3. **필터링 및 벡터 검색**: 생성된 전문가 의견(검색어)과 `State.cloth_search`의 필터를 함께 사용하여 벡터 DB를 검색합니다.
4. **K개의 후보군 확보 및 캐싱**: 각 전문가는 검색 결과(상의/하의 Top-K)를 확보합니다. 이 결과는 즉시 **`State`의 `expert_search_cache` 필드에 저장(캐싱)**됩니다.
5. **첫 결과 제시**: 시스템은 캐시에 저장된 각 전문가별 결과 목록에서 **가장 첫 번째(1순위) 코디 세트**만을 사용자에게 우선적으로 보여줍니다.

### 다. 캐시 검색 (Fast Feedback) 과정 - "다음 거 보여줘"

1. **캐시 확인**: 사용자가 "다음 거 보여줘"라고 입력하면, `search_subgraph`의 진입 라우터는 `State.last_updated_fields`의 `['__SHOW_CACHED__']` 플래그를 보고 '캐시 검색' 모드로 동작합니다.
2. **LLM/벡터 검색 생략**: 이 모드에서는 비용이 많이 드는 **전문가 의견 생성과 벡터 검색 과정을 완전히 건너뜁니다.**
3. **다음 결과 로드**: 시스템은 `State.expert_offsets`(몇 번째 결과를 보여줬는지 기억)를 참조하여, `State.expert_search_cache`에 저장된 **다음 순번(2순위)의 코디 세트**를 즉시 가져옵니다.
4. **중복 방지 및 결과 제시**: `State.shown_in_product_ids`를 확인하여 이미 보여준 상품이 아닌지 검사한 후, 새로운 코디 세트를 사용자에게 거의 즉각적으로 보여줍니다.

## 3. Musinsa API 연동 및 LLM Tool 활용: "실시간 정보로 똑똑하게"

본 시스템은 LLM이 가진 언어 능력의 한계를 극복하고, 실제 쇼핑몰의 **실시간 정보**를 바탕으로 답변을 생성하기 위해 '무신사(Musinsa) API'를 연동하고 이를 LLM이 사용할 수 있는 '도구(Tool)'로 제공했습니다. (이는 `1. 아키텍처`의 `시나리오 1`에서 사용된 `product_info_agent`의 핵심 기능입니다.)

나아가, 잦은 API 호출로 인한 성능 저하와 비용 문제를 해결하고, 더욱 복잡한 사용자 요구에 지능적으로 대응하기 위해 **도구를 통합하고 지능형 캐시 시스템을 도입**하여 시스템을 한 단계 더 발전시켰습니다.

### 가. 문제 정의: 실시간 정보의 필요성

패션 시장의 상품 정보(가격, 재고, 리뷰, 할인율)는 수시로 변합니다. 만약 미리 학습된 데이터에만 의존한다면, 사용자에게 품절된 상품을 추천하거나 잘못된 가격을 알려주는 등 치명적인 오류를 범하게 될 것입니다. 저희는 **LLM에게 실시간으로 외부 세계(웹)에 접근할 수 있는 창을 열어줌**으로써, 언제나 가장 정확하고 최신 정보를 바탕으로 추천을 제공하도록 설계했습니다.

패션 시장의 상품 정보(가격, 재고, 리뷰)는 수시로 변하기 때문에 실시간 정보 연동은 필수적입니다. 하지만 이는 또 다른 문제, 즉 **성능과 비용**의 문제를 야기합니다. 모든 요청마다 외부 API를 호출하는 것은 응답 시간을 느리게 만들고, 잠재적인 API 호출 제한(Rate Limit)에 부딪힐 위험이 있습니다. 저희는 LLM에게 실시간 정보 접근 능력을 제공하는 것을 넘어, **"어떻게 하면 더 빠르고, 더 효율적이며, 더 똑똑하게 정보를 제공할 것인가?"** 라는 문제에 집중했습니다.

### 나. 기술적 과제와 해결: 3계층(Service-Adapter-Handler) 아키텍처

이 기능 구현의 핵심은 **Musinsa가 공식 API를 제공하지 않는다**는 점이었습니다. 저희는 크롬 개발자 도구의 '네트워크' 탭을 활용하여 웹사이트가 내부적으로 통신하는 API를 역추적하는 과정을 거쳤습니다.

하지만 이렇게 찾아낸 API의 응답 데이터는 LLM이 직접 사용하기에는 너무 복잡하고 불필요한 정보가 많은 '날 것(Raw)'의 상태였습니다. 이 문제를 해결하기 위해 저희는 다음과 같은 **3계층 아키텍처**를 설계하여 적용했습니다. 그리고 그 위에 **지능형 캐시 및 비동기 처리 계층**을 추가로 도입했습니다.

**1. 3계층 아키텍처** 

1. **Service (`MusinsaAPIWrapper`)**: 가장 낮은 레벨의 계층입니다. 역추적한 API 엔드포인트에 HTTP 요청을 보내고, 서버로부터 받은 **가공되지 않은 원본 JSON 데이터를 그대로 반환**합니다.
2. **Adapter (`ProductAdapter`)**: 중간에서 데이터 정제를 담당하는 변환기입니다. 서비스로부터 받은 복잡한 JSON 데이터 중 **LLM에게 꼭 필요한 핵심 정보만 추출하고 간결한 문자열이나 딕셔너리 형태로 가공**합니다. (예: "리뷰 요약: 총 520개의 리뷰, 평균 평점 4.8점")
3. **Handler (`ProductToolHandlers`)**: 가장 높은 레벨에서 에이전트와 직접 소통하는 계층입니다. 에이전트의 도구 호출을 받아 `Service`로 원본 데이터를 요청하고, `Adapter`로 데이터를 가공한 뒤, 최종적으로 **LLM 친화적인 깨끗한 데이터를 에이전트에게 반환**하는 '감독'의 역할을 합니다.
- `Service`를 호출하여 원본 데이터를 가져오고,
- 가져온 데이터를 `Adapter`에 전달하여 LLM 친화적인 형태로 가공한 뒤,
- 최종적으로 가공된 깨끗한 데이터를 에이전트에게 반환합니다.

이러한 3계층 분리 구조를 통해, 복잡한 외부 API와의 통신 로직을 체계적으로 관리하고, LLM이 언제나 고품질의 정제된 정보만을 사용하도록 보장하여 시스템 전체의 안정성과 성능을 크게 향상시켰습니다.

**2. 지능형 캐시 및 비동기 처리 도입** 

불필요한 API 호출을 방지하고 응답 속도를 극대화하기 위해 2단계 캐시 전략과 비동기 작업을 도입했습니다.

- **Redis (휘발성 인메모리 캐시)**: '최신순 리뷰 요약'처럼 특정 조건으로 자주 요청되지만, 영구 보관할 필요는 없는 데이터를 **단기 캐시**합니다. 빠른 읽기/쓰기 속도를 활용하여 즉각적인 응답 성능을 보장합니다.
- **MongoDB (영구 캐시/DB)**: '가장 유용한 리뷰 요약'처럼 정보 가치가 매우 높고, 재생성 비용이 비싼 핵심 데이터는 MongoDB에 **영구적으로 저장**하고 관리합니다.
- **Task Queue (비동기 백그라운드 작업)**: MongoDB에 캐시를 업데이트하는 것처럼 시간이 걸릴 수 있는 DB 쓰기 작업을 백그라운드로 위임합니다. 이를 통해 사용자는 DB 작업이 끝날 때까지 기다릴 필요 없이 즉시 응답을 받을 수 있습니다.

### 다. ReAct 에이전트의 지능적 동작 방식:

위 아키텍처를 통해 준비된 '도구'들을 에이전트는 **ReAct(Reason + Act)**라는 원칙에 따라 지능적으로 사용합니다. 이는 단순히 모든 도구를 실행하는 비효율적인 방식이 아닌, '추론 -> 행동 계획 -> 실행 -> 관찰 -> 최종 행동'의 체계적인 사이클을 따르는 것을 의미합니다.

**상황 예시**: 사용자가 "이 셔츠 새로 올라온 리뷰 위주로 요약해줘" 라고 질문

1. **1단계: 추론 (Reason)**
에이전트(LLM)는 스스로에게 질문합니다. "사용자는 '최신 리뷰 요약'을 원한다. `get_product_reviews` 도구의 `sort` 인자를 `'new'`로 설정해서 호출하면 되겠다."
2. **2단계: 행동 계획 수립 (Act - Plan)**
에이전트는 이제 **단 하나의 통합된 도구**를 호출하는 훨씬 단순한 계획을 생성합니다.
    
    ```json
    "tool_calls": [
      {
        "name": "get_product_reviews",
        "arguments": { "product_id": 12345, "sort": "new" }
      }
    ]
    
    ```
    
3. **3단계: 도구 실행 및 관찰 (Observation - Black Box)**
LangGraph 프레임워크는 이 지시를 `ProductToolHandlers`에 전달합니다. 에이전트에게 이 과정은 '블랙박스'이지만, 내부적으로는 다음과 같은 정교한 워크플로우가 실행됩니다.
    - **① 캐시 확인:** 핸들러는 `sort='new'` 조건을 인지하고, 먼저 **Redis**에서 `tool-cache:product:12345:reviews:sort_new` 키가 있는지 확인합니다.
    - **② (Cache Miss 시) API 호출:** Redis에 캐시가 없으면, `Service`를 통해 Musinsa API를 호출하여 최신 리뷰 원본 목록을 가져옵니다.
    - **③ (Cache Miss 시) 내부 LLM 호출:** 가져온 원본 리뷰들을 **내부 요약 LLM(2차 LLM)**에 전달하여 '최신 리뷰'에 대한 요약문을 생성합니다.
    - **④ (Cache Miss 시) 캐시 저장:** 생성된 요약문을 다음 요청을 위해 **Redis에 저장**합니다.
    - **⑤ 결과 반환:** 최종 요약문이 에이전트에게 반환됩니다. (만약 ①에서 Cache Hit가 발생했다면, ②~④ 과정은 모두 건너뛰고 즉시 결과가 반환됩니다.)
4. **4단계: 최종 답변 생성 (Act - Respond)**
도구 실행 결과(요약문)를 전달받은 에이전트는 이를 바탕으로 자연스러운 한국어 답변을 생성합니다.
    
    > "네, 문의하신 셔츠의 최신 리뷰를 요약해 드릴게요. 전반적으로 만족도가 높지만, 일부 사용자들은 사이즈가 조금 작게 나왔다는 의견이 있었습니다."
    > 

### 라. 에이전트가 사용하는 도구 목록 (간소화 및 고도화)

기존의 세분화된 10개의 도구는 **역할 기반의 3개의 강력한 통합 도구**로 재편되었습니다. 이를 통해 LLM은 더 적은 선택지 내에서 더 쉽고 정확하게 판단할 수 있습니다.

- **`get_product_details`**: 제품의 핵심 정보(가격, 브랜드, 판매량, 좋아요, 구매 옵션, 다른 색상)를 **한 번에 병렬로 조회**하여 종합적으로 제공합니다.
- **`get_product_reviews`**: 단순 리뷰 조회를 넘어, **내부적으로 캐시(Redis, MongoDB) 확인, 갱신 여부 판단, 실시간 요약(내부 LLM 호출)까지** 처리하는 지능형 리뷰 정보 도구입니다.
- **`get_product_sizing_info`**: 사이즈 추천과 상세 실측 정보 조회의 두 가지 관련 기능을 하나의 도구로 통합하여 제공합니다.

## 4. SSE를 통한 스트리밍 통신: "실시간 대화 경험 구현"

AI의 답변을 기다리는 동안 느끼는 지루함을 없애고, 마치 실시간으로 대화하는 듯한 사용자 경험(UX)을 제공하기 위해 **SSE(Server-Sent Events)** 방식의 스트리밍 통신을 구현했습니다.

### 가. 스트리밍의 필요성 및 사용자 경험 개선

기존의 방식은 AI의 모든 작업(의도 분석, 정보 수집, 검색, 답변 생성)이 끝날 때까지 사용자가 아무런 피드백 없이 기다려야 했습니다. 이는 수 초 이상의 지연을 유발하여 사용자 경험을 저해합니다.

반면, SSE 스트리밍 방식은 **작업이 진행되는 과정 자체를 사용자에게 실시간으로 중계**하여, 시스템이 멈춘 것이 아니라 나를 위해 열심히 일하고 있다는 인식을 줍니다. 본 시스템은 **FastAPI**의 `StreamingResponse`와 `LangGraph`의 스트림 기능을 결합하여, 메신저 앱에서 상대방이 메시지를 입력하는 것을 실시간으로 보는 듯한 경험을 제공합니다.

### 나. 시스템 전체의 비동기 데이터 흐름

사용자의 메시지 하나가 최종 답변으로 돌아오기까지의 전체 시스템 흐름은 다음과 같습니다.

1. **(Front-End)**: 사용자가 메시지를 입력하고 '전송' 버튼을 누릅니다.
2. **→ (Spring Server)**: 백엔드 서버는 요청을 받아 AI 서버로 즉시 전달하는 중개자(Proxy) 역할을 합니다.
3. **→ (AI Server - FastAPI)**: LangGraph 에이전트가 작업을 시작합니다.
4. **← (SSE Connection)**: AI 서버는 작업이 끝나기를 기다리지 않고, **즉시 클라이언트와 SSE 연결을 엽니다.**
5. **← (실시간 업데이트 전송)**: 이후 그래프의 각 노드가 실행되거나 LLM이 답변을 생성하는 매 순간, 다음과 같은 업데이트가 SSE 연결을 통해 실시간으로 클라이언트에 전송됩니다.
    - `"type": "status", "content": "사용자 의도 분석 중..."`
    - `"type": "status", "content": "스타일 전문가 의견 생성 중..."`
    - `"type": "token", "content": "이런"`
    - `"type": "token", "content": "스타일은"`
    - `"type": "token", "content": "어떠세요?"`
    - `"type": "message", ...` (최종 추천 결과)

### 다. AI 서버 구현: FastAPI와 LangGraph 연동

AI 서버(FastAPI)는 다음과 같은 구조로 실시간 스트리밍을 처리합니다.

1. **FastAPI 비동기 엔드포인트**: FastAPI에 `/stream`과 같은 API 엔드포인트를 `async def`로 정의하고, 반환 타입을 `StreamingResponse`로 지정합니다. 이 `StreamingResponse`는 '비동기 제너레이터' 함수를 인자로 받습니다.
2. **초기 상태 설정**: AI 서버는 요청을 받으면, `handle_user_input` 함수를 통해 `LangGraph` 실행에 필요한 초기 `State`와 `RunnableConfig`를 설정합니다. 이 과정에서 `thread_id`를 사용하여 이전 대화 상태를 DB에서 불러와 연속성을 보장합니다.
3. **LangGraph 스트림 호출 (`agent.astream`)**: 답변이 모두 생성될 때까지 기다리는 `ainvoke` 대신, **`astream`** 메소드를 호출하여 그래프 실행을 시작합니다. 이때 `stream_mode`를 설정하여 필요한 모든 종류의 데이터를 스트림으로 받아옵니다.
    - `stream_mode=['updates', 'custom', 'messages']`
        - `'updates'`: 각 노드(기능)의 실행이 완료되었을 때의 최종 결과물(예: 완성된 추천 메시지)
        - `'messages'`: LLM이 답변을 생성할 때, 단어(토큰) 단위로 생성되는 과정 (타이핑 효과 구현용)
        - `'custom'`: 저희가 직접 정의한 중간 작업 상태(예: "의도 분석 중...")
4. **데이터 생성 및 실시간 전송 (`yield`)**:
엔드포인트의 비동기 제너레이터 함수(`message_generator`)는 `agent.astream`으로부터 실시간으로 쏟아지는 데이터 조각들을 반복문으로 처리합니다.
`yield` 키워드를 통해 데이터 조각이 반환될 때마다, `StreamingResponse`는 이를 즉시 클라이언트로 전송(Push)합니다.
5. **스트림 종료**: 그래프의 모든 작업이 끝나면, 제너레이터는 `{"type": "[DONE]"}` 메시지를 마지막으로 전송하고 스트림 연결을 정상적으로 종료합니다.

### 라. 효율성과 확장성을 고려한 SSE 메시지 구조 설계

클라이언트(프론트엔드)가 다양한 종류의 스트리밍 데이터를 명확하게 구분하고 처리할 수 있도록, 표준화된 JSON 메시지 구조를 설계했습니다.

**1) 기본 메시지 타입**
모든 메시지는 SSE 표준에 따라 `data:` 접두사와 함께 전송되며, `type` 필드를 통해 종류를 구분합니다.

- **`type`**: 메시지의 종류를 나타내는 핵심 필드입니다.
    - `status`: AI가 현재 어떤 작업을 하고 있는지 알려주는 **상태 메시지**입니다. (예: "코디 검색 중...") 클라이언트는 이 메시지를 받아 로딩 스피너나 상태 텍스트를 표시합니다.
    - `token`: LLM이 답변을 생성하는 **실시간 타이핑 효과**를 위한 텍스트 조각입니다. 클라이언트는 이 메시지를 받을 때마다 글자를 하나씩 이어 붙여 보여줍니다.
    - `message`: 추천 결과와 같이, 하나의 노드 작업이 완전히 끝나고 생성된 **완성된 메시지**입니다.
- **`content`**: 실제 데이터가 담기는 필드입니다. `type`에 따라 다른 구조의 데이터가 담깁니다.

**2) 핵심 설계: 'refer' 타입을 이용한 데이터 분리 (Lazy Loading)**

가장 중요한 설계 원칙은 이미지 URL과 같은 **무거운 데이터를 SSE 스트림으로 직접 전송하지 않는 것**입니다.

- **문제점**: 추천 상품의 이미지 URL, 특히 보안을 위해 임시로 생성되는 AWS Pre-signed URL은 문자열의 길이가 매우 깁니다. 여러 상품을 추천할 때 이 긴 URL들을 모두 SSE 스트림에 담아 보내는 것은 네트워크에 큰 부담을 주며, 스트리밍의 장점인 '가벼움'과 '신속성'을 저해합니다.
- **해결책**: '지연 로딩(Lazy Loading)'과 '참조(Reference)' 방식을 결합했습니다.
    1. **ID만 전송**: AI 서버는 추천 상품의 URL 대신, `message` 타입의 SSE 메시지 내 `additional_kwargs` 필드에 **`"type": "refer"`** 라는 특별한 플래그와 함께 **상품 ID 목록(`product_ids`)**만을 담아 보냅니다.
        
        ```json
        // SSE로 전송되는 '참조' 메시지 예시
        data: {
          "type": "message",
          "content": {
            "type": "ai",
            "content": "이런 스타일의 코디는 어떠세요?",
            "additional_kwargs": {
              "type": "refer",
              "product_ids": ["P12345", "P67890"]
            }
          }
        }
        
        ```
        
    2. **클라이언트의 후속 요청**: 클라이언트(프론트엔드)는 `type`이 `refer`인 메시지를 받으면, 여기에 포함된 `product_ids`를 가지고 백엔드(Spring 서버를 경유)에 **별도의 REST API(`GET /api/search/{product_id}`)를 호출**하여 각 상품의 상세 정보(이미지 URL, 가격, 브랜드 등)를 요청합니다.

**3) API 응답 최적화: Redis 캐시와 Task Queue를 활용한 비동기 처리**

클라이언트가 요청하는 `GET /api/search/{product_id}` 엔드포인트는 단순한 DB 조회가 아닌, **성능과 안정성을 극대화하기 위한 다단계 처리 로직**을 수행합니다.

1. **1단계: Redis 캐시 확인 (가장 빠른 경로)**
    - 요청이 들어오면 가장 먼저 **Redis 캐시**에 해당 상품 데이터가 있는지 확인합니다.
    - **Cache Hit**: 데이터가 존재하면, 만료되었을 수 있는 이미지 URL만 AWS S3 Pre-signed URL로 새로 발급하여 즉시 사용자에게 응답합니다. 이 과정은 100ms 미만으로 매우 빠릅니다.
2. **2단계: Cache Miss 시 병렬 조회**
    - 캐시에 데이터가 없으면, **MongoDB**에서 상품의 메타 정보를 가져오는 작업과 **Musinsa API**에서 실시간 가격 정보를 가져오는 작업을 `asyncio.gather`를 통해 **동시에 병렬로 실행**하여 대기 시간을 최소화합니다.
3. **3단계: 실시간 정보 기반 응답 및 비동기 후처리**
    - **(API 호출 성공 시)** 최신 가격 정보와 DB 정보를 조합하여 **사용자에게 즉시 응답을 반환**합니다. 사용자는 더 이상 기다릴 필요가 없습니다.
    - 동시에, 이 새로운 정보를 **캐시와 DB에 업데이트하는 느린 작업을 `TaskQueue`(ARQ)에 '작업(Task)'으로 등록**합니다. (`src/taskqueue/client.py`)
    - 별도의 **Worker 서버**(`src/taskqueue/worker.py`)가 이 작업을 비동기적으로 가져가 백그라운드에서 데이터 업데이트를 처리합니다. 이를 통해 **사용자 응답 시간과 무거운 백그라운드 작업을 완벽하게 분리**했습니다.
4. **4단계: 안정성을 위한 폴백(Fallback) 메커니즘**
    - 만약 Musinsa API 호출이 **실패(예: 429 Rate Limit 에러)**하더라도, 시스템은 에러를 반환하는 대신 MongoDB에 저장된 **기존 가격 정보를 사용하여 사용자에게 응답**합니다. 이 '폴백' 메커니즘 덕분에 외부 API의 일시적인 문제에도 서비스는 중단 없이 안정적으로 동작합니다.
