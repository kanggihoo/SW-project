자연어 기반의 의류 이미지 검색을 위해 **Atlas Vector Search**를 활용하고 있으며, 데이터는 다음과 같이 구성되어 있군요.

- **`products`**: 모든 색상에 공통적인 제품 정보 (이름, 브랜드, 가격, 캡션 등)
- **`product_skus`**: 색상, 사이즈 등 개별 옵션(SKU)에 따른 고유 정보 (색상명, 이미지, 스타일 태그 등)
- **`images`**: 제품의 다양한 각도와 색상별 대표 이미지 URL
- **`embedding`**: 실제 벡터 검색의 대상이 되는 캡션 정보의 벡터값
- **`reviews`**: 사용자들이 작성한 리뷰 텍스트

## 비정규화

이 가이드는 MongoDB Atlas Vector Search의 성능을 극대화하고, 색상과 같은 세부 조건으로 필터링 기능을 구현하기 위해 기존 데이터 구조를 변환하는 전체 과정을 안내합니다.

### **기존 구조 (As-Is): 상품 중심 모델**

현재 데이터는 **상품 하나당 하나의 문서**로 구성되어 있습니다. `product_id`가 문서의 고유 키(`_id`) 역할을 합니다.

- **구조적 특징**:
    - `products`, `embedding`, `reviews` 필드에는 모든 색상에 적용되는 **공통 정보**가 저장됩니다.
    - `product_skus` 필드 안에는 `sku_id`, `color_name`, `image_urls` 등 각기 다른 색상(SKU) 정보가 **여러 개의 배열(Array) 형태**로 병렬적으로 저장되어 있습니다.
    
    ```json
    // 기존 구조 예시
    {
      "_id": "4149670", // Product ID
      "products": { "product_name": "SL01 섬머 데님 와이드 팬츠", ... },
      "product_skus": {
        "sku_id": ["4149670_그레이", "4149670_데님", ...],
        "color_name": ["그레이", "데님", ...],
        ...
      },
      "embedding": { ... }
    }
    ```
    
- **주요 한계점**:
"회색(그레이) 제품만 검색"과 같이 특정 SKU의 속성으로 필터링하는 것이 매우 비효율적이고 복잡합니다. Vector Search 전에 필터링을 적용하기 어려운 구조입니다.

### **목표 구조 (To-Be): SKU 중심 모델**

새로운 데이터 구조는 **SKU(색상) 하나당 하나의 문서**로 구성됩니다. 이제 `sku_id`가 문서의 고유 키(`_id`)가 됩니다.

- **구조적 특징**:
    - 기존의 공통 정보(`products`, `embedding` 등)는 각 SKU 문서에 **중복 저장**됩니다. (비정규화)
    - `product_skus` 필드는 `product_sku`(단수형)라는 이름의 **단일 객체(Object)**로 변경되어 해당 SKU의 정보만 담습니다.
    
    ```json
    // 목표 구조 예시 1: '그레이' 색상 문서
    {
      "_id": "4149670_그레이", // SKU ID
      "products": { "product_name": "SL01 섬머 데님 와이드 팬츠", ... },
      "product_sku": {
        "sku_id": "4149670_그레이",
        "color_name": "그레이",
        ...
      },
      "embedding": { ... }
    }
    ```
    
- **핵심 장점**:
`product_sku.color_name`처럼 필터링하려는 속성에 직접 접근할 수 있어 **인덱싱과 사전 필터링(pre-filtering)이 매우 용이**해집니다. 이는 검색 속도와 정확도를 크게 향상시킵니다.

### **2단계: 마이그레이션 계획 수립**

운영 중인 서비스의 안정성을 보장하는 것이 가장 중요합니다.

- **신규 컬렉션 생성**: 기존 컬렉션(`products`)은 절대 직접 수정하지 않습니다. 대신, 변환된 데이터를 저장할 **완전히 새로운 컬렉션**(`products_by_sku`)을 생성합니다.
- **원본 데이터 보존**: 마이그레이션 중 문제가 발생하더라도 원본 데이터는 그대로 보존되므로 롤백이 용이하고 서비스 중단 위험이 없습니다.

### **3단계: 마이그레이션 스크립트 구현**

Python의 `pymongo` 라이브러리를 사용하여 변환 로직을 구현합니다. 스크립트는 다음과 같은 로직으로 동작합니다.

1. **MongoDB 연결**: 소스 컬렉션과 타겟 컬렉션에 연결합니다.(기존의 db 설정 및 연결 설정 코드 이용)
2. **소스 컬렉션 순회**: `original_products` 컬렉션의 모든 문서를 하나씩 읽어오는 반복문(loop)을 시작합니다.
3. **공통 데이터 추출**: 반복문 안에서 `products`, `embedding`, `reviews` 등 중복 저장될 공통 정보를 변수에 할당합니다.
4. **SKU 데이터 분해**: `product_skus` 필드 내의 배열 길이만큼 반복하는 두 번째(내부) 반복문을 실행합니다.
5. **신규 문서 조립**: 내부 반복문 안에서 각 SKU에 해당하는 신규 문서를 생성합니다.
    - `_id`는 해당 순번의 `sku_id`로 설정합니다.
    - 추출해 둔 공통 데이터를 그대로 복사해 넣습니다.
    - `product_sku` 객체를 만들고, `color_name` 배열의 `i`번째 값, `color_hex` 배열의 `i`번째 값 등을 채워 넣습니다.
6. **배치(Batch) 삽입**: 생성된 신규 문서들을 리스트에 모아두었다가, 일정 개수가 되면 `insert_many()`를 사용하여 `products_by_sku` 컬렉션에 한 번에 삽입합니다. 이는 성능을 크게 향상시킵니다.
